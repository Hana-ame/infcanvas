# infcanvas 设计文档

> 2026-08-03 · 从 gsap-framework 拆出的独立项目
> 历史实现/追加记录见 `docs/CHANGELOG.md`；当前进度见 `docs/PROGRESS.md`。

## 0. 北极星（north star）

**这个游戏的最高目标 = 模拟一个现实的社会。**

一切机制（自主 AI、旧版决策层信仰、意图失真、工厂物流、派系战争、亚空间）
都是手段，都在为"让一个虚拟社会真实地自己运转"服务。
设计取舍时用这个问题来检验：**这样做是让社会更真实，还是只是更像游戏？**

## 1. 定位与核心概念

**一句话：模拟一个现实社会的实时模拟——RimWorld 的地块深度 + Dwarf-Fortress 的自主小人 + 工厂物流链（戴森球计划式）+ 玩家不是指挥官而是旧版决策层。**

玩家**不逐个指挥小人**。小人有自己的目标（由 LLM + 确定性 AI 驱动），
玩家在**特定条件下影响小人的目标层**，让小人目标随玩家而动——玩家是改变世界的力场，
不是遥控器。

| 项 | 决定 |
|---|---|
| 类型 | 现实社会模拟（自主文明 + 旧版决策层干预） |
| 渲染 | infinite canvas：世界 = 单张连续地图 canvas/WebGL(Pixi)，UI = DOM |
| 时间 | 纯即时（不可暂停，可选倍速），观察演化 |
| 联机 | 是（最终目标），WSS（专用服务器） |
| LLM | 小人目标决策 + 野生旧版决策层 + 事件生成 + 建筑/城镇/工厂规划 |
| 插件 | mod：新增物品、新 AI、新事件、新建筑、新旧版决策层能力 |
| 玩家角色 | 旧版决策层（oracle）：通过教堂影响来教堂的人 |
| 目标 | 纯沙盒，无胜负 |
| 玩家身份 | 可切换：先以个体小人扮演，也可转为旧版决策层 |
| 世界 | 单张连续地图（infinite canvas），相机任意平移缩放 |

## 2. 核心张力：意图失真（intent loss）

**游戏的根本张力 = 玩家想影响世界，但世界不完全听你的。**

玩家与小人之间存在三层信息损耗，这是玩法核心而非缺陷：

```
玩家意图 ──【LLM 理解偏差】──▶ 旧版决策层表达 ──【小人个体利益过滤】──▶ 实际行为
```

1. **LLM 理解偏差**：旧版决策层 → LLM → 意图，LLM 特性决定了它不能 100% 理解玩家意图（这是 LLM 固有特性，不是 bug，是风味）
2. **小人个体利益**：玩家的利益 ≠ 小人的利益。小人有个体利益、性格、信仰，可能不执行甚至违背旧版决策层
3. **信息盲区**：亚空间等区域玩家完全不可见，只能靠预置指令间接影响

> "玩家和 LLM 斗智斗勇" = 上述链路自然产生的博弈，不是刻意的对抗设计。

## 3. 玩家 = 旧版决策层（oracle）交互模型

```
RimWorld:   玩家 ——点选→ 小人执行具体命令（去采矿、去建造）
infcanvas:  玩家 ——施加影响→ 小人目标层 → 小人自主决定怎么执行
```

- 玩家对某个小人/派系施加"旧版决策层影响"（祝福、指引、警告、启示）
- 旧版决策层影响进入 **LLM 慢决策层的上下文**，改变小人的 long-term goal
- 微观执行（怎么走路、什么时候吃饭）永远由确定性 AI 完成
- 玩家不是无能为力：旧版决策层影响够强就能改变小人的路线，但小人仍是自主的

### 旧版决策层影响范围：影响圈 + 来教堂的行为选择

- **影响圈 = 教堂的吸引力范围**：只在影响圈内，小人的卡池才出现"参拜"这张卡（或参拜卡权重受距离调制——越近权重越高）
- **来教堂 = 一个行为选择，走抽卡机制**（宗教系列卡）：抽 3 选 1 时，参拜 vs 干活的**收益对比**决定来不来
- **太忙不会来**：忙人的参拜收益低（状态/收益调制），干活卡收益压过参拜——旧版决策层影响力 = 教堂吸引力 × 小人空闲度 × 信任度
- 常来教堂的小人受旧版决策层影响更深（信任度累积），从不来的人不受影响
- 这让旧版决策层有**地理性 + 时间性**：玩家要影响一个忙碌的社会，要么让教堂更吸引人（布道/仪式/信物），要么等他们闲下来
- 待定：旧版决策层是"单个小人"级还是"派系/城镇"级

### 玩家身份可切换

- **开局**：可以扮演一个具体小人，或直接扮演旧版决策层
- **随游戏进程**：扮演的小人可以创建宗教/成为旧版决策层；旧版决策层也可选中某小人使其单独收到"指挥"
- 视角身份是连续的，不是两个割裂模式

### 旧版决策层通过教堂发布（核心约束）

旧版决策层**不能凭空施法**——旧版决策层影响必须通过**神庙/教堂**这个物理实体发布：

- 玩家必须先让小人建造教堂，旧版决策层才能在教堂发布影响
- 旧版决策层只能在教堂"降下"，教堂是旧版决策层与世界的唯一物理接口
- 不同教堂可传播不同教义，玩家可建立多个教堂网络
- 教堂是世界可见的建筑，可被异教派系**毁坏**（信仰博弈的物理表现）
- **亚空间里不准建教堂**（亚空间不可见，旧版决策层影响力无法触及）

### 野生旧版决策层（AI 旧版决策层）

**旧版决策层不只有玩家。** LLM 会扮演天然的野生旧版决策层（"分发旧版决策层的天然 AI"），
它们拥有自己的教堂、信誉度，并主动传教：

- 野生旧版决策层自主建立教堂，向小人发布影响，与小人的利益/派系互动
- 玩家旧版决策层与野生旧版决策层**竞争信徒**——同一批小人的信任度会被多个旧版决策层争夺
- 这是"玩家 vs LLM 斗智斗勇"的核心：不只是玩家影响世界，还有 LLM 旧版决策层在影响世界
- 玩家可能让小人"改信"自己的教堂，也可能被野生旧版决策层抢走信徒

### 教堂怎么建立

- 小人自主建（受旧版决策层引导后自主决定）——默认路径
- 旧版决策层玩家引导建（间接，旧版决策层决定建在哪）——玩家路径
- 两种都存在，同一世界里共存

### 信誉度 + 信任度（双维度信仰系统）

| 维度 | 含义 | 机制 |
|---|---|---|
| 旧版决策层信誉度 | 玩家作为旧版决策层的长期声望 | 发布准确的指引（让小人受益）→ 涨；发布误导/虚假指引 → 跌 |
| 教堂信任度 | 单个小人/派系对**某个教堂**的信任 | 每个教堂独立累积；小人受该教堂旧版决策层影响的能力 = 信任度决定 |

- 小人会对某个教堂的旧版决策层产生**信任或不信任**——信任度低的小人可能无视该教堂的旧版决策层
- 信仰博弈：同一旧版决策层在不同教堂发布，效果因小人对各教堂信任度而异
- 信誉度高 → 小人更愿意建教堂/追随；信誉度低 → 旧版决策层逐渐失去影响力
- 这是"玩家利益 ≠ 小人利益"的又一体现：小人可以不信，信仰是争取得来的

### 小人可编程：插槽系统（同源机制）

**小人是可以被编程的**——信仰足够高时，旧版决策层可以为小人设置行为逻辑。
L258 原则成立：**行为指令集不经过 LLM，确定性概率执行**，LLM 只控制概率。

#### 插槽系统（类似 DNA/天赋槽）

每个小人身上有固定数量的**插槽**，旧版决策层把行为指令"插"进去：

- **槽位数量**：天生固定槽数 + 可解锁潜能槽（信越深/成长越多槽）
- **可替换**：槽内指令可换，但**更换需要走事件**（不是随时改）
- **凹小人**：玩家通过筛选小人（天生槽数/属性）+ 后天培养，凑出理想配置
- **DNA/天赋 = 天赋卡**：小人生成时由 DNA 决定，以**天赋卡**形式占用槽位（被动修正卡：天生蛮力、夜猫子体质、心灵手巧）；DNA 同时决定槽位数量与布局——DNA 是底子，槽位 + 天赋卡是它的表现
- **统一卡模型**：天赋卡 / 技能卡 / 习惯卡 / 旧版决策层旧版指令卡都是同一种卡，区别只在来源与可否移除：

  | 卡来源 | 谁给 | 可否移除 | 例 |
  |---|---|---|---|
  | 天赋卡 | DNA（生成固定） | 不可（或极难，走事件） | 天生蛮力、夜猫子体质 |
  | 技能卡 | 学习/练习 | 可（遗忘退化） | 射箭熟练 |
  | 习惯卡 | 反复行为养成 | 可（改不掉的老毛病） | 酗酒、早起 |
  | 旧版决策层旧版指令卡 | 信仰解锁插入 | 可（换槽走事件） | 白天传教、入夜警戒 |

- **槽内容两类**：
  1. **下一个目标选项**（带触发权重）——小人的"下一个目标"从插槽中按权重挑选
  2. **行为规则**（`当 X 时 → 做 Y`）——触发式行为约束

#### LLM 只印卡和触发事件（不碰选择过程）

**LLM 完全不进入行为选择链路**，只有两个职责：

1. **印卡**：创建/插入新卡（旧版决策层旧版指令卡、野生旧版决策层的卡、事件奖励的卡）——LLM 生成卡的内容和初始权重，之后选择过程与 LLM 无关
2. **触发事件**：事件通过**统一接口调整卡的权重/收益**（"村外发现矿脉"事件 → 挖矿卡权重 +50）——LLM 只改世界，不改小人

- 行为选择的权重调整全由确定性机制完成（环境/状态/事件/性格）
- LLM 零延迟零成本压力：印卡和事件都是低频、异步、批量可做
- 意图失真保留：LLM 印的卡要小人信任才进槽（信仰/信任度过滤）

#### 事件触发 = 状况匹配的事件列表（不写死）

事件系统是**数据驱动的事件列表**，系统每轮从"符合当前状况"的列表里选事件，不把触发逻辑写死在代码里：

- 每个事件 = `condition(ctx)`（**状况匹配**：只有当前局面满足才进候选池）+ 效果（改资源/建单位/调卡权重/记历史）
- 例：有农田才"丰收"、有余粮才收留"流浪者"、开过矿洞才"发现矿脉"、人口≥3 才可能"瘟疫"、有物资才"游商到访"、整体低落才"庆典"
- 候选池再叠加 `weight`（权重）/ `cooldown`（冷却）/ `minTime`（开 X 秒后可触发）调制
- **LLM 接入点 = provider 可插换**：P0 用确定性脚本列表；P1 把 provider 换成 LLM 生成的事件（同一 `ScriptedEvent` 接口），LLM 只印卡 + 触发事件，不进选择链路

#### 执行模型（抽卡，无合成器）

```
小人 DNA（生成时固定）→ 决定天赋 + 槽位数 + 槽位布局
        ↓
卡池 = 基础卡 + 天赋卡 + 技能卡/习惯卡 + 旧版决策层旧版指令卡(信仰过滤)
        ↓
定时 check: 按权重抽 3 张（不放回，种子化）
        ↓
3 张中挑收益最高的执行（收益表每日重算一次）
        ↓
生成 job → 事件 → COC 骰子判定 → 结果 → 日志 / 熟练度 / 权重调整
```

- **与亚空间预置指令同源**：亚空间航行中玩家无法实时指挥，同一套插槽/指令系统 = 唯一控制方式
- **意图失真保留**：概率不是 100%，小人本性可违抗，但高信仰 + 凹好的插槽可接近"编程感"
- 这是"信仰 = 控制权"的落点：信仰累积到足够高 → 解锁插槽 → 编程小人行为

### 旧版决策层资源的约束

- 旧版决策层影响不能无限用（防止变成变相遥控器）
- 机制候选：冷却时间 / 信仰值（信仰越足，影响越强）/ 影响力点
- 待定：旧版决策层是"单个小人"级还是"派系/城镇"级

### 旧版决策层的情报流：拒绝全知

旧版决策层的信息**不能来自上帝视角**，只能来自教区情报流：

- 情报来源 = 教堂/祭司视角的观察：报告、传言、信件、人口统计——滞后、片面、可能失真
- **未建教堂的区域 = 盲区**（与亚空间同类），旧版决策层不知道那里发生了什么，只能间接影响
- 情报失真成为机制：传言会变形（参考 DF 传闻系统），祭司可能隐瞒或夸大
- 盲区是世界显得"独立于玩家"的第一手段；全知 + 无约束干预 = 变相遥控器（WorldBox 教训）

### 历史系统：仿真日志（Legends 式）

历史不是"事后编的故事"，而是**仿真日志**：

- 每次确定性事件结构化记录：实体、地点、时间、因果链（谁对谁做了什么）
- 事件系统是一等公民：可查询、可导出、可回放（DF Legends 可导出千年历史）
- **LLM 只做叙述润色**（把日志写成编年史/歌谣），不产生事实——事实只能来自 sim
- 世界生成时先跑"零玩家策略游戏"：seed 生成地形后确定性模拟数百年历史，玩家开局看到的废墟、旧战场、仇敌关系全部来自这段仿真，而非随机点缀（Qud 历史生成的约束满足思想：每片区域至少被提及一次，事件不能与已有历史矛盾）
- 历史是旧版决策层的感知窗口之一（与情报流互补：历史是全的但可能没人告诉你）

## 3. 世界模型：多派系自主文明

AI 不止管一个殖民地——小人在世界各处自主建镇、扩张、互相战争：

```
世界（infinite canvas，分块生成）
 ├─ 派系 A   ── 城镇 ├─ 建筑 ── 居民（pawn）
 │                   └─ 首领（LLM 决策）
 ├─ 派系 B   ── 城镇 ── ...
 └─ 无派系群体（流浪者、野人营地）
```

- **派系关系**：友好/中立/敌对，随事件与战争演化
- **城镇**：AI 规划选址、扩张、建造（选址 = LLM 慢决策，施工 = job 系统确定性执行）
- **战争**：派系间攻防（目标 = LLM 决策，战斗/行军 = 确定性 AI）
- 玩家可以有自己的"信徒派系"，也可以只当旁观旧版决策层

### 小人的欲望系统（利益驱动 + 经济咬合）

**经济系统的意义 = 满足小人的欲望，不是抽象 GDP。小人利益 = 欲望满足程度。**（意图失真的机制层落点：小人的利益 ≠ 玩家的利益）

**欲望结构（checkpoint 机制）**：

- **欲望类型 = 七宗罪**（中世纪神学框架，与旧版决策层/教堂主题同构）：

  | 罪 | 驱动行为 | 满足方式 |
  |---|---|---|
  | 暴食 gluttony | 进食、享乐 | 食物、酒宴 |
  | 懒惰 sloth | 逃避工作 | 休息、清闲 |
  | 贪婪 greed | 囤积 | 财产、资源占有 |
  | 嫉妒 envy | 攀比 | 相对地位、压过他人 |
  | 傲慢 pride | 被尊重 | 声望、头衔、崇拜 |
  | 暴怒 wrath | 攻击 | 发泄、暴力胜利 |
  | 色欲 lust | 繁衍 | 伴侣关系 |

- 每个小人**先天有罪孽倾向**（性格权重：天生暴怒者 vs 天生谦和者），环境与事件改变后天权重
- **七美德（谦卑/慷慨/贞洁/耐心/节制/勤奋/慈善）是对立轴**——教堂宣扬美德，小人天然倾向罪孽，信仰系统因此有道德维度
- 每个欲望有**数个 checkpoint**（阈值分档）：满足 → 勉强 → 匮乏 → 危急
- **定期检查**（非每 tick——欲望变化慢，检查也慢，每隔一段时间运行一次，比对已有资源/环境是否满足欲望）
- 检查结果驱动行为权重偏移：需求未满足的欲望在 job 选择中权重升高

**每日记录**：

- 每天把满足程度写入"欲望满足史"
- 满足史进三层记忆（暗记忆凝练为"长期不满"等印象），影响 LLM 对小人心理状态的判断

**不满足的后果（梯度行为变化）**：

| 档位 | 行为 |
|---|---|
| 轻微不满 | job 选择权重偏移，优先做满足欲望的事 |
| 中等不满 | 个人需求 job 抢占派系 job（DF 式高优先级需求，不可取消） |
| 严重不满 | 行为模式变化 + LLM 决策上下文注入"不满"状态（过激倾向） |
| 恶意槽激活 | 长期不满足累积恶意计数器，达阈值激活**恶意槽**：反社会行为——偷窃、抢劫、暗算、背叛、参与叛乱 |

- 恶意槽 = 意图失真的极端表现：旧版决策层要他虔诚，他饿肚子就会去偷
- **恶意槽 = 罪孽累积**：长期不满足的罪孽把行为推向该罪的过激形态——暴怒→暴力、贪婪→偷窃抢劫、嫉妒→暗算背叛、傲慢→暴政；罪孽累积进恶意槽，达阈值激活反社会行为
- 参考：Songs of Syx 死亡螺旋（资源短缺→不满连锁→暴动→崩溃）、DF 需求 job 抢占、CK3 阴谋/压力系统

**与经济系统的咬合**：

- 欲望满足需要经济资源（食物/住房/工具/奢侈品），经济瓶颈 → 欲望不满 → 行为变化 → 社会动荡
- 资源短缺是小范围的（某个镇缺粮），不满就是局部的——欲望系统天然产生区域性社会压力

**与旧版决策层的关系**（干预杠杆，不违反"不直接指挥"）：

- **纵容型影响**：满足罪孽（赐酒宴、纵容复仇、赏财富）——见效快，但长期腐蚀社会（B&W 教训：邪恶路线快而毁）
- **美德型影响**：导向美德（布道压制罪孽权重、宣扬七美德）——慢、可持续，但压抑可能反弹（欲望越压越烈）
- 重塑型影响：改变欲望权重（贫困时引导转向信仰，"富人靠科技穷人靠神"），不动经济只动欲望结构
- 七宗罪 × 七美德的轴心让旧版决策层的每次干预都有道德代价——选择纵容还是压抑，本身就是世界叙事

### 小人的属性与骰子判定（COC 式角色卡）

**每个小人 = 一张 COC 式角色卡。骰子不裁决动作，裁决事件成败**——决策链：

```
触发决策(欲望checkpoint / LLM意图 / job) → 决策 → 生成执行事件 → 骰子裁决事件成败 → 结果入日志
```

- 骰子只出现在"决策之后、事件落定之前"，不做动作级判定（走路/吃饭不掷骰）
- 事件失败 → 进恶意槽/事件素材；确定性实现：骰子 = 种子 RNG 封装（`SimRng.d100()`），回放可复现

**属性卡**（COC 八属性）：

| 属性 | 含义 | 影响 |
|---|---|---|
| STR 力量 | 体力 | 近战、搬运、建造 |
| CON 体质 | 健康 | HP、抗病 |
| SIZ 体型 | 体格 | HP、负重 |
| DEX 敏捷 | 灵活 | 闪避、命中、手工 |
| APP 外貌 | 魅力 | 社交、信仰传播 |
| INT 智力 | 思维 | 技能学习、施工精度 |
| POW 意志 | 精神 | **对抗欲望**、抗压、SAN 上限 |
| EDU 教育 | 知识 | 技能起点、科技 |

**技能**：百分制（1-100），工作/社交/战斗/感知四类，由 defs 注册（mod 可加新技能）。

**判定**（掷 d100 对抗技能/属性值，成功度分级）：

| 掷骰结果 | 等级 | 后果 |
|---|---|---|
| ≤ 技能值 | 成功 | 正常效果 |
| ≤ 技能值/2 | 困难成功 | 更优效果 |
| ≤ 技能值/5 | 极限成功 | 最佳效果 |
| 01-05 | 大成功 | 暴击，超出预期 |
| 96-100 | 大失败 | 灾难 → 进恶意槽/事件素材 |

- **对抗检定**：双方事件冲突时各自掷骰比成功度（战斗、说服、偷窃、传教）
- **只对有风险、有意义的事件掷骰**（COC 原则）：骰的是攻击事件、技能使用事件、社交对抗、危险行动，不是日常行为
- **确定性实现**：骰子 = 种子 RNG 封装（`SimRng.d100()`），结果记录进"历史=仿真日志"（谁对谁掷了什么），LLM 只润色叙述（"他这一剑几乎劈开了甲胄"）——AI Roguelite 同构：LLM 决策 + 骰子裁决，数值永远在引擎侧

**POW 对抗欲望**（与七宗罪系统咬合）：

- 压抑罪孽 = POW 检定：失败 → 当场冲动满足罪孽（暴怒者挥拳、贪婪者顺手牵羊）
- 长期压抑失败累积 → 恶意槽；POW 高的圣人 vs POW 低的凡人——**美德修行本质是 POW 训练**
- 旧版决策层的布道/祝福可临时提升 POW 检定（美德型干预的机制落点）

**SAN 理智**（对接创伤记忆）：

- 目睹死亡/恐怖/疯狂事件 → SAN 下降；低 SAN → 狂乱发作（短期疯癫行为：跑走/发呆/攻击），是"行为变化"的极端档
- 恢复途径：休息、教堂告解（旧版决策层的干预杠杆）；SAN 永久损伤 → 长时记忆固化（DF 创伤记忆的 COC 化）

**技能成长**（COC 经验规则）：

- 使用技能后掷 d100，> 当前值则 +1d10——越用越强，边际递减
- 小人的"人生" = 技能曲线 + 欲望史 + 记忆，全进三层记忆的暗记忆凝练

**战斗流程**：

```
LLM 定战略意图(进攻/包围/撤退) → 确定性层移动/接敌 → 生成攻击事件 → 骰子裁决事件成败 → 结果入日志
```

- LLM 永远不掷骰、不算伤害；骰子只在事件层裁决（避免骰子风暴）
- mod 接口：新技能/新属性 defs 注册、判定钩子（自定义检定规则）

### 空间模型：亚坐标精度 + 区块系统

**混合精度模型（Factorio 式，非 RimWorld 全贴格、非全连续）**：

| 保持 tile 格子的（逻辑层） | 连续 float 的（物理层） |
|---|---|
| 地形类型 / 可走性 / 资源分布 per-tile | 实体位置（世界单位） |
| **建筑 footprint 贴格** | 碰撞 = 圆形半径（≈0.3 格） |
| chunk 划分 / 生成 / 流式 / 持久化 | 移动轨迹、速度 |
| 寻路图（nav grid = tile，不细化） | 交互距离（工作点偏移，非贴邻格） |

- 地形/建筑必须贴格：生成、覆盖层、寻路可走性、流式全依赖格子，全连续则"资源在哪/墙挡路没"都要浮点几何判断
- 实体连续：pawn 不跳格，工作站在目标旁的任意偏移点（如砍树站在 `(3.5, 4.2)`）
- 碰撞发生在建筑边界（线段/矩形 vs 圆），墙格在寻路图中标记不可走

**坐标系约定**：

```
世界单位(float, 权威) ──/tileSize──► tile 坐标(int) ──/chunkTiles──► chunk 坐标(int, 可负)
```

- 逻辑运算（寻路、footprint、资源判定）用 tile；物理运算（移动、碰撞、距离）用世界单位；权威永远是世界单位
- chunk 键为整数对（支持负坐标），实体坐标以整数 tile 为权威，渲染坐标派生（浮点漂移只影响画面）

**移动链路**（分层不变，执行变连续）：

```
目标点 ─► grid A*(tile 可走性) ─► 路径点列表 ─► 连续寻迹 + 避让(steering) ─► 平滑位置
```

**区块系统：双图层模型**

无限地图不可能全量存储，chunk 拆两层：

```
chunk(64×64 tile) = 生成层(确定性地形, 不落盘) + 覆盖层(玩家/AI 改动, 才存储)
                         ↑                              ↑
        seededRng(chunkX, chunkY) 即得           建筑/采空资源/道路 = 与生成层的差异
        任何人重生成结果一致                        覆盖层才需要持久化和网络传输
```

- **活跃半径**：只有玩家/派系附近的 chunk 参与 tick，远的休眠（不 tick、不占内存）——同时解决 sim 性能、内存上限、网络流式范围
- **流式协议**（消息形状现在定，P2 实现）：`S→C: chunkData { x, y, terrain[], entities[], defsRev }`；`C→S: watchArea { center, radius }`（客户端报视口，服务端决定发什么）
- **实体驱逐语义**：实体不随 chunk 驱逐——`entityId → chunkId` 索引保持，chunk 卸载只丢地形数组，实体列表单独驻留或序列化进覆盖层
- **P0 范围**：种子确定性生成（惰性 getChunk(x,y)）、稀疏存储 + 负坐标、客户端按视口加载/卸载渲染对象、双图层数据结构（覆盖层先放内存 Map）
- **留待 P2**：覆盖层持久化/落盘、休眠驱逐（活跃半径模型）、压缩传输、watchArea

**亚坐标带来的连带变化**：

- **空间索引**：chunk 内挂 spatial hash（bucket ≈ 1 tile），碰撞查询取本 chunk + 邻居 chunk 的索引，chunk 边界无感
- **job 到达判定**：`distance < workRadius`（float 比较），workRadius 是 def 数据而非写死"两格相邻"
- **确定性**：浮点在单机服务端上确定性成立（同输入同顺序同结果），回放复现依然成立；跨机器确定性已放弃（server-authoritative）
- **渲染**：连续位置让客户端插值更平滑

## 5. 权威模型：server-authoritative（TS 双端共用）

- **权威仿真 = TS sim**，P0 单机跑浏览器内，P1 联机跑 Node server（20Hz tick），客户端渲染（60fps）+ 插值
- **sim 逻辑一份，双端复用**——P1 时 server 直接 import `src/sim`，无双写成本
- 锁步确定性同步放弃（AI 复杂、浮点非确定）；但 **roll/骰子用种子化 RNG**（回放可复现）
- 客户端只发命令（move/build/harvest + 旧版决策层影响），服务端校验后执行
- **分块生成**：server 生成 chunk 流式下发，server 是唯一事实源

### ECS：sim 的核心架构

**ECS 是必须的**——它是整个 sim 的地基，双端共用（P0 浏览器 / P1 Node server 同一套）。

- **方案**：bitecs（TS 最成熟的纯数据 ECS，零依赖，序列化友好，联机同步天然契合）
- **SoA 布局**：组件存数组而非对象，实体 = id，系统按数组批量遍历
- **确定性**：系统顺序固定 + 种子化 RNG（SimRng），同输入同顺序同结果，回放可复现
- **序列化**：ECS 纯数据 → 快照/增量同步直接用结构化数据，P1 联机消息不卡壳
- **SIMD 化（后续）**：TS 可用 WebAssembly/SIMD 加速批量系统，P0 不需要，P3 性能优化再上

### LLM 与权威模型

- **LLM 决策必须在服务端执行**——多客户端各自调 LLM 会状态分叉，破坏一致性
- 客户端不持有 API key，只接收 LLM 决策结果（作为正常 sim 更新）
- 服务端 LLM 网关：排队、超时、重试、成本控制
- LLM 决策结果 = 印卡 + 事件（详见 §6 决策模型），作为正常 sim 更新注入，行为选择 100% 确定性

## 6. 决策结构（LLM 关键设计）

LLM 延迟是秒级，游戏 tick 是 20Hz。分层，LLM 永远不进主循环：

```
┌─────────────────────────────────────────────┐
│ 旧版决策层输入（玩家）◄──────────────────────────── │
└──────────────────────┬──────────────────────┘
┌──────────────────────▼──────────────────────┐
│ 慢决策层（LLM，异步，秒级）                    │
│   · 小人 long-term goal（受旧版决策层影响）          │
│   · 派系决策（建镇选址/扩张/宣战/外交）          │
│   · 事件生成（流浪者/灾害/商队/奇遇）            │
│   · 只印卡 + 触发事件，不碰行为选择            │
├─────────────────────────────────────────────┤
│ 快决策层（确定性 AI，20Hz）                   │
│   · 抽卡选择 / 寻路 / job 执行 / 战斗          │
│   · 完全确定性，无 IO，离线可跑                 │
├─────────────────────────────────────────────┤
│ sim 核心（确定性，20Hz）                      │
└─────────────────────────────────────────────┘
```

- LLM 输出 = 结构化**卡/事件**（印新卡、触发事件改权重/收益），不产生决策、不碰选择链路
- 微观行为（抽卡、寻路、施工）永远是确定性 AI，不经过 LLM
- pawn 等待 LLM 回复时挂起在"思考"状态，不阻塞世界
- **旧版决策层 = LLM 印卡的来源之一**：旧版决策层旧版指令卡由 LLM 生成内容，经信仰/信任度过滤后进卡池
- **行为指令集（旧版决策层编程）不经过 LLM**：预设指令 + 抽卡执行是确定性系统，LLM 只负责卡的存在与事件

### 决策模型：抽 3 选 1（无合成器）

行为选择没有合成器——**权重抽卡 + 收益择优**：

```
卡池(基础卡 + 天赋卡 + 技能/习惯卡 + 旧版决策层旧版指令卡)
        │ 定时 check(每 0.5 游戏日 / job 完成)
        ▼
按权重抽 3 张(不放回, 种子化) ──► 收益表(每日重算一次) ──► 挑收益最高的一张
        │
   生成 job → 事件 → 判定(COC骰子) → 结果 → 日志 / 熟练度 / 权重调整
```

- **权重 = 冲动**（性格 / 习惯 / 环境 / 状态 / 事件调整）——决定**抽到哪些卡**
- **收益 = 理性**（局势评估：饥饿 → 吃收益高；矿脉事件 → 挖矿收益高）——决定**选哪张**
- 权重与收益分离：冲动小人抽到歪卡但收益理性仍会选对的；被事件/教义大改权重时可能 3 张全歪
- **收益每日重算一次**（1day1次，低频）：性能友好 + 局势变化不会让小人秒变卦
- **LLM 完全不碰这里**：只印卡（改变卡池）+ 触发事件（事件调权重/收益），选择链路 100% 确定性
- **可读性**：旧版决策层能看到小人"闪过哪 3 个念头、选了哪个"——狗屁倒灶日志的素材
- 违抗 = 可选的附加 roll：3 张里若欲望卡（七宗罪临时卡）被抽到但收益低没被选 → 违抗 roll 改选欲望卡
- 同输入同输出：抽卡与收益都是纯函数（种子化），回放可复现

#### 插槽系统：槽位 + 旧版指令卡（完整版，P0 实现规范）

**总体结构**：

```
DNA(生成固定) → 槽位布局 + 天赋卡
                    ↓
槽位(类型/容量/优先级) ← 装载卡(天赋/技能/习惯/旧版决策层)
                    ↓
定时 check: 收集卡 → 过滤 → 调制 → 抽卡 → 目标选择 → 违抗roll → job
                    ↓
事件 → 判定(COC骰子) → 结果 → 日志 / 熟练度 / 记忆
```

**槽位（Slot，凹小人的地基）**：

| 属性 | 说明 |
|---|---|
| 数量/布局 | DNA 决定；信仰/成长可解锁潜能槽 |
| 类型 | 基础槽（生理保底）/ 系列槽（限定系列）/ 通用槽 |
| 容量 | 单卡槽 / 多卡槽（卡组，内部按权重抽） |
| 优先级 | 紧急槽 > 常规槽 > 自由槽（P1 启用，多层决策） |
| 状态 | 激活 / 休眠（事件或条件控制） |

**卡（Card，统一模型）**：

| 属性 | 说明 | 例 |
|---|---|---|
| 来源 | 天赋（DNA，不可移除）/ 技能（学习）/ 习惯（养成）/ 旧版决策层（信仰插入） | — |
| 功能 | 行为卡（抽中→做 job）/ 修正卡（改概率）/ 目标卡（行为+目标选择） | — |
| 系列 | 战斗 / 工作 / 社交 / 宗教 / 娱乐 / 生理 | — |
| 情境 | 时段（白天/黑夜/全天）+ 事件 / 位置 / 心情条件 | 战后祈祷（事件=战斗后） |
| **卡属性** | **黑夜加成 / 白天加成 / 工作兴趣加成 / 战斗兴趣 / 社交兴趣 / 耐寒 / 耐热……** | 夜猫子=黑夜加成 2.0；热爱工作=工作兴趣 1.5 |
| 权重 | 基础触发概率 | — |
| 熟练度 | 0-100：触发↑ 遗忘↓，影响权重与效果 | — |
| 解锁 | 信任度 / 技能 / 事件 | 旧版决策层旧版指令卡需信仰解锁 |

**卡属性（stat modifiers）双用途**：

- **概率调制**：check 时参与加权（黑夜加成 × 黑夜时段；工作兴趣加成 × 工作系列行为）
- **判定修正**：COC 检定加成（耐寒→严寒环境检定 +；战斗兴趣→战斗检定 +）

**基础卡（人人固有，可被替换）**：黑夜睡觉、白天干活、饥饿进食、受伤治疗——生理保底不靠卡（紧急度由状态调制保证）。插"夜猫子"顶掉"黑夜睡觉" → 昼夜节律被改写。

**卡相互作用**（P0.5+）：

- **协同**：夜猫子 + 入夜警戒 → 夜间战斗力强化（卡组 = 旧版决策层的构筑题）
- **冲突**：贪婪卡 vs 禁偷教义 → 教义赢，但产生"诱惑"事件（恶意槽 +）
- **占据**：大卡锁定系列（战争狂热 → 该系列其他卡让位）

**卡演化**（P0.5+）：

- 熟练度：触发↑ / 长期不用↓ → 权重和效果随之变化（卡 = 习惯的建模）
- 进化：熟练满 → 蜕变（"射箭熟练"→"箭术大师"）
- 腐化：恶意槽污染卡（"祈祷"→"伪善祈祷"——行为不变，意图变了）

**定时 check 机制**：

- 决策定时器每 tick 递减，**归零 → check 一次**，抽下一个 job；job 完成 → 立即 check（接续）
- 定时器间隔 = def 数据（如每 0.5 游戏日），可受状态影响（无事可做时更频繁 check）
- 与欲望 checkpoint 同源：都是"每隔一段时间运行一次"的检查器

**check 流程（抽 3 选 1）**：

```
1. 过滤：教义排除 / 情境不满足 / 未解锁
2. 调制权重：P = 卡属性(时段/兴趣加成) × 环境调制(气温/天气) × 状态调制(饥饿/疲劳/健康/SAN/心情) × 马尔可夫(上一事件) × 卡权重 × 熟练度
3. 按权重抽 3 张（不放回，种子化）
4. 收益表（每日重算一次）→ 挑收益最高的卡
5. 目标卡 → 目标选择（目标池按概率：对谁传教、打谁）
6. 违抗 roll（可选）：欲望卡被抽到但没被选 → roll 改选欲望卡
7. 生成 job → 事件 → 骰子判定 → 结果 → 日志 / 熟练度 / 权重调整
```

- **环境调制**：气温（酷暑 → 户外干活低、饮水高；寒冬 → 囤燃料）、天气（下雨 → 户外干活低、室内活动高）
- **状态调制**：饥饿 → 进食；疲劳 → 休息；健康低 → 治疗；SAN 低 → 疯癫行为进候选池；心情差 → 娱乐/发泄
- **马尔可夫**：上一事件偏置（刚打完架 → 战斗训练/休息概率上升）

**P0 范围**：槽位类型+容量、卡属性（时段/兴趣加成）、情境（时段）、行为卡+修正卡。**P0.5**：熟练度/进化/腐化、协同/冲突/占据、目标卡。**P1**：优先级分层（多层决策）。

// sim/core/rng.ts —— 种子 RNG（确定性）
export class SimRng {
  private s: number;
  constructor(seed: number) { this.s = seed >>> 0; }
  next(): number {            // xorshift32
    let x = this.s;
    x ^= x << 13; x >>>= 0;
    x ^= x >> 17;
    x ^= x << 5; x >>>= 0;
    this.s = x;
    return x;
  }
  d100(): number { return this.next() % 100 + 1; }
}

// sim/ai/cards.ts —— 插槽系统（槽位 + 旧版指令卡，数据驱动 + 注册表）
type Sin = 'gluttony'|'sloth'|'greed'|'envy'|'pride'|'wrath'|'lust';

// 系列 = 字符串 id + defs 注册（不是 union type——mod 加系列不改核心代码）
interface SeriesDef { id: string; label: string; }

// 卡属性 = 任意字符串键 → 数值字典（mod 加新属性不改 interface）
interface Card {
  id: string;
  source: 'talent' | 'skill' | 'habit' | 'oracle';  // 来源
  func: 'behavior' | 'modifier' | 'target';         // 行为/修正/目标卡
  series: string;                                    // 系列 id
  job?: string;                                      // 行为卡：对应 job
  situation: { period: 'day'|'night'|'all'; event?: string; };  // 情境
  stats: Record<string, number>;                     // 卡属性字典
  weight: number;                                    // 基础触发权重
  mastery: number;                                   // 熟练度 0-100（P0.5）
  unlock?: (p: PawnState) => boolean;                // 解锁条件
}

interface Slot {
  id: string;
  kind: 'basic' | 'series' | 'generic';   // 基础/系列限定/通用
  series?: string;                        // 系列槽限定
  capacity: number;                       // 卡容量（卡组）
  priority: 'urgent' | 'normal' | 'free'; // 紧急/常规/自由（P1 启用）
  cards: Card[];                          // 卡组（内部按权重抽）
  active: boolean;
}

// —— 注册表（mod 的全部入口，核心 checkJobs 永不改动）——
interface ModifierCtx {
  pawn: PawnState; env: EnvState; prevEvent: string;
  seriesOf: (c: Card) => string;
}
type ModifierFn = (ctx: ModifierCtx, card: Card) => number;

const seriesRegistry = new Map<string, SeriesDef>();
const cardRegistry = new Map<string, Card>();
const modifierRegistry = new Map<string, ModifierFn>();
const hooks: Record<string, Array<(prob: Record<string, number>, ctx: SimContext) => void>> = {};

export function registerSeries(def: SeriesDef) { seriesRegistry.set(def.id, def); }
export function registerCard(card: Card) { cardRegistry.set(card.id, card); }
export function registerModifier(name: string, fn: ModifierFn) { modifierRegistry.set(name, fn); }
export function registerHook(stage: string, fn: (prob, ctx) => void) { (hooks[stage] ??= []).push(fn); }

// 内置调制器（mod 可新增/覆盖，属性名 = 注册键，与卡的 stats 键一一对应）
registerModifier('night-bonus', ({ env }) => env.night ? 2 : 0.3);
registerModifier('day-bonus',   ({ env }) => env.night ? 0.3 : 2);
registerModifier('cold-resist', ({ env }, c) => env.temperature < -10 ? 1 + (c.stats['cold-resist'] ?? 0) : 1);
// 兴趣加成：只对对应系列生效（work-interest 只作用于 work 系列卡）
registerModifier('work-interest',   ({ seriesOf }, c) => seriesOf(c) === 'work'   ? (c.stats['work-interest'] ?? 1) : 1);
registerModifier('combat-interest', ({ seriesOf }, c) => seriesOf(c) === 'combat' ? (c.stats['combat-interest'] ?? 1) : 1);
// 例：mod 加"魅力加成" = registerModifier('charm-bonus', fn) + 卡 stats 写 'charm-bonus'，核心零改动

// 卡属性 → 概率调制：遍历卡 stats 字典，按属性名查调制器相乘
function cardFactor(ctx: ModifierCtx, card: Card): number {
  let f = 1;
  for (const [name, v] of Object.entries(card.stats))
    if (modifierRegistry.has(name)) f *= modifierRegistry.get(name)(ctx, card) * v;
  return f;
}

interface PawnState {
  hunger: number;      // 0-100 越饿越高
  tired: number;       // 0-100 越累越高
  health: number;      // 0-100 越低越伤
  san: number;         // 0-100 理智
  mood: number;        // 0-100 心情
  desire: Record<Sin, number>;       // 七宗罪满足度 0-100
  personality: Record<Sin, number>;  // 罪孽倾向 0-100
  obedience: number;                 // 顺从度
}

interface SimContext {
  prevEvent: string;                 // 上一个事件（马尔可夫状态）
  env: EnvState;                     // 环境：昼夜/气温/天气
  slots: Slot[];                     // 槽位（含卡组）
  doctrine: Set<string>;             // 教义禁止集合
}

// 状态调制：生理/心理紧急度提升对应行为概率（内置函数，也可注册化为调制器）
function stateFactor(p: PawnState, c: Card): number {
  switch (c.series) {
    case 'physio':  return 1 + Math.max(p.hunger, p.tired, 100 - p.health) / 40;
    case 'leisure': return 1 + (100 - p.mood) / 100;   // 心情差 → 娱乐
    default: return 1;
  }
}

// 环境调制：气温/天气（内置函数）
function envFactor(ctx: SimContext, c: Card): number {
  const e = ctx.env;
  if (c.series === 'work')
    return (e.raining ? 0.4 : 1) * (e.temperature > 35 || e.temperature < -10 ? 0.5 : 1);
  if (c.series === 'leisure') return e.raining ? 1.6 : 1;
  return 1;
}

// 马尔可夫偏置表：上一事件 → job 偏置（def 数据，mod 可改，未列出的默认 10）
const MARKOV_BIAS: Record<string, Record<string, number>> = {
  fight: { 'train-combat': 40, rest: 20, eat: 15 },
  haul:  { 'mine': 40, build: 30, eat: 10 },
  pray:  { preach: 40, 'train-combat': 15, work: 20 },
  // ...
};

function checkJobs(p: PawnState, ctx: SimContext): Record<string, number> {
  const prob: Record<string, number> = {};
  for (const slot of ctx.slots) {
    if (!slot.active) continue;
    for (const c of slot.cards) {
      if (!situationOk(c, ctx) || ctx.doctrine.has(c.job)) continue;   // 情境 + 教义排除
      prob[c.job] =
        cardFactor(ctx, c)                               // 卡属性（注册表调制器）
        * envFactor(ctx, c)                              // 环境调制（气温/天气）
        * stateFactor(p, c)                              // 状态调制（饥饿/疲劳/健康/心情）
        * (MARKOV_BIAS[ctx.prevEvent]?.[c.job] ?? 10)    // 马尔可夫偏置
        * c.weight                                       // 卡权重
        * (0.5 + c.mastery / 100);                       // 熟练度（P0.5）
    }
  }
  hooks['beforeRoll']?.forEach(h => h(prob, ctx));       // 阶段钩子（mod 插入）
  return normalize(prob);
}

// 抽取：种子 RNG，确定性
function weightedRoll(prob: Record<string, number>, rng: SimRng): string {
  const total = Object.values(prob).reduce((a, b) => a + b, 0);
  if (total <= 0) return 'idle';
  let r = rng.next() % total;
  for (const [job, w] of Object.entries(prob)) {
    r -= w;
    if (r < 0) return job;
  }
  return 'idle';
}

// 收益：每日重算一次（1day1次），局势评估——饥饿/环境/目标/事件修正（def 数据）
function computeUtility(p: PawnState, ctx: SimContext, c: Card): number {
  let u = 0;
  if (c.series === 'physio')   u += Math.max(p.hunger, p.tired, 100 - p.health) / 2;
  if (c.series === 'work')     u += ctx.taskUrgency(c.job);       // 派系任务紧迫度
  if (c.job === 'pray')        u += ctx.nearChurch() ? 20 : 0;    // 教堂影响圈内
  u += ctx.eventBoosts[c.job] ?? 0;                               // 事件调整收益
  return u;
}

// 每日重算收益表
function updateUtilities(p: PawnState, ctx: SimContext) {
  for (const c of ctx.cardPool) c.utility = computeUtility(p, ctx, c);
}

// 抽 3 选 1：按权重抽 3 张（不放回），挑收益最高
function pickJob3(prob: Record<string, number>, rng: SimRng): string {
  const drawn: string[] = [];
  const pool = { ...prob };
  for (let i = 0; i < 3 && Object.keys(pool).length > 0; i++) {
    const job = weightedRoll(pool, rng);
    drawn.push(job);
    delete pool[job];                          // 不放回
  }
  return drawn.reduce((best, j) =>
    utilityOf(j) > utilityOf(best) ? j : best, drawn[0]);
}

// 决策定时器：归零或 job 完成 → check
export function tickPawnDecision(p: PawnState, ctx: SimContext, rng: SimRng): string | null {
  ctx.timer -= 1;
  if (ctx.timer > 0 && !ctx.jobJustFinished) return null;
  ctx.timer = ctx.checkInterval(p);            // 重置定时器（def 数据）
  if (ctx.dayRolled) updateUtilities(p, ctx);  // 每日重算收益（1day1次）
  return pickJob3(checkJobs(p, ctx), rng);     // 抽 3 选 1 → 新 job
}

**确定性保证**：sim 主 RNG 流 = `new SimRng(世界种子 ^ tick)`,所有 roll/骰子共用同一流按序取——回放只需重放外部输入（命令/事件）即可复现。

### LLM 上下文打包：世界摘要 + 三层记忆

LLM 的上下文不能塞整个世界，参考 RimWorld RimMind 模组（已被社区验证）分层打包：

| 层 | 内容 | 存续 |
|---|---|---|
| 活跃记忆 | 近期事件（按时间排序，容量上限） | 短期 |
| 存档记忆 | 按重要度排序，满时淘汰低重要度条目 | 中期 |
| 长期印象（暗记忆） | AI 每日凝练 ≤50 字摘要，永久保留 | 长期 |

- 每次 LLM 请求 = **世界摘要**（派系/城镇/经济/威胁的压缩状态）+ 相关事件史 + 目标个体记忆 + 旧版决策层影响
- 只在事件节点打包，控制 token（参考：RimWorld 实测每事件 7k-13k token，5 年约 2M token）
- 记忆由 sim 事件自动采集（工作/受伤/死亡/关系/派系事件），非手动编写

### 叙事压力（narrative pressure）

LLM 天然爱重复生成同类事件，需要确定性计数器约束多样性：

- 记录"距上次袭击/贸易/疾病/来访 X 天"，生成压力值进入 prompt
- 例：45 天无袭击 → 战斗类压力高 → 即使殖民地平和也倾向触发冲突事件
- 事件多样性靠计数器逼出来，不靠提示词

### 小人社交对话与流言系统（狗屁倒灶）

小人之间的闲聊八卦、勾心斗角是乐趣核心之一，也让社会显得真实可笑。参考 RimMind-Dialogue（拦截社交事件 → LLM 生成上下文对话 → 效果注入心情/关系，已有先例）。

**频率分层（成本关键）**：

| 层级 | 内容 | 生成方式 |
|---|---|---|
| 微互动 | 碰面打招呼、抱怨、表情 | 确定性模板（高频、零成本） |
| 闲聊 | 引用近期事件/记忆的对话 | LLM 批量生成（服务端异步，无人等待） |
| 深聊/冲突 | 关系变化、重大事件、背叛 | LLM 按需调用（低频、重要节点） |

- 每小人每日 LLM 对话限额，超限回落模板
- 对话必须引用记忆（三层记忆是素材库），否则空洞

**对话 = 流言系统（产物是"话题"，不是文本）**：

- 一次对话产出话题单元：谁、对谁、说了什么、涉及谁
- 话题沿社交网络传播（八卦），传播改变他人对该小人的看法（名声/信誉）
- 流言 → 关系 delta + 心情 thought + 记忆条目，闭环进系统（Smallville 已验证：LLM 社会能自发产生信息扩散）

**旧版决策层窗口**：

- 对话/流言日志是玩家可读的观察窗口（"文明新闻流"的微观层）
- 旧版决策层可通过教堂布道影响话题传播方向（引导舆论，间接干预）

**效果挂钩系统（不是装饰）**：对话必须落成关系变化/心情 thought/记忆条目，否则小人只是说话机器。

## 7. 插件/mod 系统（与联机的冲突点）

### 分层原则：服务端 mod（逻辑）+ 客户端 mod（表现）

| 层 | 谁能写 | 内容 | 在哪里执行 |
|---|---|---|---|
| 服务端 mod | 房主/服主 | 物品、新 AI、新事件、新 job、新建筑、新旧版决策层能力 | **只有服务端执行** |
| 客户端 mod | 任意客户端 | 渲染表现、UI、立绘、音效 | 客户端本地（不影响逻辑） |

保证：**逻辑统一在服务端，客户端 mod 只是皮肤**，联机一致性不被破坏。

### 数据驱动注册表（defs）

```ts
registerDef({ kind: 'item', id: 'steel', stackable: true });
registerDef({ kind: 'building', id: 'solar-panel', size: 3, power: 30 });
registerBehavior({ kind: 'ai', id: 'my-pawn-ai', decide: (ctx) => Intent });
registerEvent({ kind: 'event', id: 'wanderer-arrives', weight: 2 });
register旧版决策层({ kind: 'oracle', id: 'bless', cost: 10, effect: (ctx) => ... });
// 插槽系统（见 §6）：系列/卡/调制器/钩子全部注册表化
registerSeries({ id: 'research', label: '研究' });
registerCard({ id: 'study-late', series: 'research', stats: { 'night-bonus': 2 } });
registerModifier('charm-bonus', (ctx, card) => ...);   // 新卡属性 = 新调制器，核心零改动
registerHook('beforeRoll', (prob, ctx) => ...);          // check 流程阶段钩子
```

**扩展性原则（核心 sim 代码永不改动）**：

- 加新卡属性 = `registerModifier` + 卡 stats 加键，不改 interface/switch
- 加新系列 = `registerSeries` + 卡 def，不改 union type
- 加新卡 = `registerCard` 纯数据（除非要新行为逻辑）
- 调平衡 = 改 def 数值，不重编译
- 加 check 阶段 = `registerHook`
- 验证标准：**任何 mod 能力都应能通过注册表实现，不需要改 sim 源码**；做不到的注册表接口，是 sim 的缺陷

- 服务端加载 mod → 注册进注册表 → 流式下发 defs 给客户端（只读副本）
- 版本校验：客户端 defs hash 必须匹配，否则拒绝加入

### 物品
- 物品 = 数据（id、可堆叠、质量、标签）+ 可选行为钩子
- 存储在地块/库存中，由 job 系统搬运
- mod 新增物品 = 一个 def，零代码（除非要新行为）

### 新 AI
- 新 AI = 注册一个新的 `decide` 函数（纯逻辑，双端共享）
- 服务端 mod 可替换/叠加小人决策逻辑，或**新增派系 AI**
- 客户端不能执行 mod AI（一致性），只能收到结果

## 8. 网络协议（WSS，Node server）

- 传输 WSS，JSON 帧起步，性能不够换二进制（msgpack）
- Node 侧用 `ws` 起步，压不动换 `uWebSockets.js`
- C→S：`join` `command(move/build/harvest)` `oracle(施加旧版决策层)` `speed/pause` `ping`
- S→C：`world snapshot` `tick delta` `entity events` `chunk data` `world clock` `defs(只读)`
- sim 双端同源，协议类型定义在 `src/shared/protocol.ts`，无需双实现

## 新增 DLC 架构设计（2026-08-20 追加）

### zone 系统（区域）
- 玩家划定矩形区域 + tag（work/home/storage/forbid）
- 其他系统通过 `ctx.getCap('zone')?.inZone(x, y, type)` 查询
- `zone` 命令：add/remove 区域
- 设计：纯查询服务，不驱动行为——行为系统读 zone 过滤目标

### hot-cold 系统（热区/冷区/前线/后方）
- 热区（front）：检测 15 格内敌人 → active → 自动征召 + 建筑损坏
- 冷区（rear）：安全区域 → 自动解除征召（指挥官除外）
- 3s 节流检测，`hotcold` 命令划定/删除
- 设计：复用 K_DRAFTED 征召键，零新机制

### work-priority 系统（职业优先级）
- 指派职业 utility +10（影响抽卡权重）
- `ctx.getCap('workPriority')?.getBonus(eid)` 查询
- 5s 节流（优先级不频繁变化）

### diplomacy 系统（派系外交）
- 多营地间关系 -100~+100（对称存储）
- >50 自动贸易（+资源+关系），<-50 可宣战
- 关系自然漂移向 0，10s 节流
- `ctx.getCap('diplomacy')` 提供 getRelation/adjustRelation

### belt 系统（传送带物流）
- 4 方向传送带（上下左右）+ 通用版
- 链式搬运（产出点→传送带→仓库），每秒 0.5 单位
- 2s 节流，cellSize=8 空间哈希查下游

### masterpiece 系统（工匠杰作）
- 高熟练(skill≥80)产出时 5% 概率 → 带名字+制造者的杰作
- 监听 work_completed 事件 → roll → 写篝火记忆 + 发事件
- 种子原则：零品质评估链

### gossip-facts 系统（传闻事实）
- 所有事件 → 事实文本 → 篝火记忆 → 社交系统自然引用
- bus.onAny 监听（跳过内部事件防噪声）
- 种子原则：零新系统逻辑

### ruins 系统（旧世界遗迹）
- 世界生成时放置废墟（hp=0 + meta.ruin）
- 小人走近 2 格 → 发现 → logEvent + addMemory
- 5s 节流检测，3-6 个遗迹随机分布

### story 包（故事模板）
- 20 个 ScriptedEvent：自然/社交/灾难/机遇/传奇 5 类
- 每个事件 = condition + run → 事件系统自然 roll 触发
- adjustMoodAll 能力通过 step:before hook 挂载

### extra-needs 包（数据驱动需求）
- DLC 可注册新需求类型（hygiene/entertainment 等）
- need-defs.ts 注册表 + NeedsComp.custom Map
- tickNeedsBatch 自动衰减 + setNeedField/adjustNeedField 支持

### 新增群系/敌人/事件/建筑/服饰
- biomes-2：丛林/草原/苔原 + 黑豹/狼/猛犸
- enemies-2：狼群/巨熊/掠夺者/虫群/石巨人
- events-2：瘟疫/丰收/迁徙/火山/商队
- buildings-3：陷阱/医院/学校/市场/竞技场/信号塔
- clothing-3：鞋/手套/面具/披肩（4 部位 × 2 材质 = 8 新穿戴物）


## 新增战斗玩法架构（2026-08-20 追加）

### weapons 武器系统
- 武器 = 物品（meta.weapon = { dmg, range, cd, type }）→ wear 命令装备 → 武器系统读 meta 射击。
- 科技树：火药(3) → 燧发枪 → 步枪 → 机枪(5) / 冲锋枪(4)；火药 → 大炮(5) + 炮兵。
- 兵种：骑兵（高速冲锋 dash）/ 装甲车（500HP 厚）/ 炮兵（远程重击）。
- 设计：LOS 门——无视野的敌人不能射击（巷战转角遭遇）。

### urban-combat 巷战视野
- Bresenham 射线投射 LOS：逐格推进遇 barrier 建筑（墙/碉堡/胸墙）→ 遮挡。
- 视野范围 = 基础 12 + z 差 ×4（站得高看得远）；0.5s 节流；只算征召/指挥官。
- 能力：ctx.getCap('vision') → canSee/visibleCount/hasLOS；weapons 射击前查 LOS。

### fortifications 战场工事
- 种子原则：工事 = 建筑 + tag（barrier/defense/fortify）→ raid 遍历时自然消费。
- 拒马/鹿角/铁丝网 = 经行伤害/减速；地堡/碉堡 = 藏人 + 射击；炮台基座 = 射程 ×1.5。

### 运行时热挂载（mountPack）
- ModPack.subpacks 嵌套：大 DLC = 小 DLC 组合（DLC 商店拆装）。
- Sim.mountPack：游戏运行中挂载新 DLC——新系统增量装配（下一 tick 生效）、新建筑同步 World、新命令即用。

## 从零重来 v3 架构（2026-08-21 追加：阶段①+② 当前态）

> 上文所有章节描述旧版全量实现（归档 test/，历史保留）。本节为当前代码真实架构。

### 内核（src/sim，零 DOM 零 Node API）

- **Sim**：实体表 + `step(dt)` 系统驱动 + 命令路由（move 引擎内建，其余走注册面）+ 事件环缓冲。
  Sim 实现 SimContext——玩法包只见切面不见本体，最小 ctx 即可单测任意系统。
- **决策引擎 behavior（内核唯一内联系统）**：每 tick 每鼠「到期抽卡 → commit（写当前卡/
  到期时刻/统计/熟练度成长）→ 每 tick 执行 action → 到期重抽」。对需求、工作、玩法零知识；
  兜底卡 `_stun` 仅防空轮死循环（正常局永远抽不到，闲逛等种子由玩法包提供）。
- **权重管线（原则①的落地）**：`w = base × ΣcardWeight钩子 × 特质seriesMul × (0.5+mastery/100)`，
  条件过滤后轮盘赌。没有行为树/任务队列/优先级 if——饥饿只是把某系列推高，抽不到就忍着。
- **熟练度 = 卡的演化**：触发 +masteryGain 封顶 100；未触碰按流逝时间惰性衰减
  （存储 {v,t}，读时折算），权重 ×(0.5+m/100)——卡即习惯。
- **World 无限地图（2026-08-21 大改版：分形海拔场驱动全部地形）**：
  - **分形海拔场 E(x,y)∈0..1**：三八度值噪声加权和（大陆架 32 / 山脉 14 / 细节 6，
    权重可调），湖泊、滩涂、丘陵、岩层**全部由同一张海拔图按阈值切带**，彼此天然衔接：
    `E<waterLevel→水域`；`<+shoreBand→滩涂泥地`；`<hillLevel→草地`；`<stoneLevel→丘陵 z=1`；
    `≥stoneLevel→岩层 z=2`。草地上留 dirtChance 碎土斑。
  - **林地密度场**：moisture 噪声高处树锚点率 ×groveBoost——森林成片而非均匀撒点。
  - **瓦片缓存**：tileAt 结果 memoize（容量封顶清空即重推，确定性无损）——分形海拔
    比单哈希贵一个量级，渲染/A* 高频查询必须缓存。
  - **多格特征**：树=2×2 对齐锚点大树（锚点率受密度场调制），**树冠阻挡通行**、产量 4~6 木；
    浆果丛 1×1 可穿行，且不与树冠重叠（两套撒点互斥）。特征查询以锚点为唯一代表
    （收割/避让键一致）。
  - **多格建筑**：BuildingDef 支持 w×h 占地（pos=左上角），整体落子/拆除/占格；
    同类间距按矩形外扩一圈判定；棚屋升为 2×2。
  - 工作卡邻接按"点到占地矩形距离"判定；寻路落点取占地周边最近可走格
    （World.nearestFreeAdjacent）。出生安全区无水/石/特征不变。
  - **一切格子查询入口 Math.round 量化**（连续坐标哈希会造出幻影特征——真实踩坑）。
- **A\***：**8 邻域（斜角禁切）+ 手写二叉堆 + 八距离启发 + 双档迭代预算**（≤24 格 1500 / 远距离 8000），
  失败返回空路径=涌现输入（去不了就换行为），调用方禁止无视失败站桩。
- **z 高度模型（2026-08-21 用户裁定：废除二元可通行，改用 z 值）**：
  地形表带海拔（草/泥 0、岩层 2、水为液体不可立足）；单位带 climb 攀爬
  （鼠 1 上不去岩层、猫 2 可登台追猎）；移动合法性 = 目标可立足 且 |Δz| ≤ climb。
  **寻路谓词随之升级为按边 4 参 stepOk(from→to) + goalOk(终点立足)**——按格二元判定
  在高差模型下没有意义。刷怪落点必须为低地 z=0 可立足格（岩层孤岛会造成双向僵局）。
  **整数量化入口铁律**：小人坐标连续，起终点必须 Math.round 再进 A*——浮点 key 曾解码错位、
  半路重规划整条返回空（逃跑卡形同虚设）。工作卡对寻路失败的目标做单槽避让（30s 内不再抽该卡），
  防"看得见够不着"的抽卡死循环；闲逛落点只挑可通行格。

## R1 联机还账架构（2026-10-05 追加：阶段④已知限制清零）

本节记录 R1-1..R1-5 的设计决定。核心诉求只有一个：**把「联机」从能跑通变成能长期开着玩**。

### 8.1 分层：把可测的部分从副作用里剥出来

R1 的五项全部是「网络 + 定时器 + IO」三类副作用的组合。直接写进 RemoteSim/gameserver 就只能靠真实等待来测——
退避要等 15 秒、看门狗要等 15 秒，CI 上必 flaky。因此本轮先把判定逻辑抽成**纯函数层**，副作用留在薄壳里：

| 模块 | 职责 | 副作用 |
| --- | --- | --- |
| `client/reconnect.ts` | 退避曲线、看门狗判定 | 无（`backoffMs` / `shouldWatchdogTrip` / `BackoffState`） |
| `client/interp.ts` | 插值数学、双缓冲槽 | 无（`lerpPos` / `clamp01` / `interpK` / `InterpSlot`） |
| `client/selection.ts` | 框选几何判定 | 无（`eidsInRect` / `normalizeRect` / `rectContains`） |
| `server/auth.ts` | 握手/管理命令鉴权 | 无（`authorizeHandshake` / `authorizeAdmin` / `timingSafeEqualStr`） |
| `server/save-store.ts` | 存档名→路径、读写 | 有（fs），但路径安全规则本身是纯函数 |

薄壳（`remote.ts` / `game-server.ts` / `render.ts`）只负责「调纯函数 + 执行副作用」。
这样退避曲线、插值系数、框选边界、鉴权分支都能毫秒级断言，不用起服务器。

### 8.2 R1-1 心跳与看门狗：为什么是「服务端主动发」

心跳帧由服务端每 `PING_MS`(10s) **无条件**广播，客户端判定「链路活着」的规则是
「距上次收到**任何**消息超过 `WATCHDOG_MS`(15s)」即判定假死并主动断开重连。

三个决定值得记下：

1. **服务端主动发单向帧**，而不是客户端 ping / 服务端 pong。单向帧就够判定活性，
   不必为 pong 多加一条消息类型与状态机；而且上行通不代表下行通（NAT/代理下），
   服务端主动发才能同时探测两个方向。
2. **无条件发**，不看「有没有变化」。看门狗要的是「链路还活着」的证据；
   靠内容变化推断活性，会在静止的世界里误判假死（鼠全在睡觉 → 没有任何变化 → 误杀连接）。
3. **阈值关系 `WATCHDOG_MS > PING_MS`** 是硬约束（15s > 10s）：
   若阈值 ≤ 心跳周期，丢一次心跳就会误杀。这条已写成断言锁在测试里。

**为什么要主动断开**：TCP 半开连接（拔网线 / 笔记本合盖 / NAT 超时）时 socket 收不到 `close`，
界面却「看起来还连着」——玩家会一直对着一张冻结的世界点右键。主动 `close()` 会触发 `onclose`，
从而汇入正常的退避重连路径。

**重连必须复用原 URL（含 `?token=`）**。这是与 R1-2 联动的坑：只记 host:port 会在开了鉴权的服务器上永远被拒。

**`close(1008)` 不重连**：鉴权失败重连多少次都不会成功，白白消耗退避计数、让玩家等一个不可能的结果。
服务端把「你 token 错了」和「网络断了」用不同的 close code 区分开，客户端据此决定要不要再试。

### 8.3 R1-2 鉴权：两条独立的门

鉴权在 `server/auth.ts` 里有**两条互不相同**的门，因为它们防的是不同的人：

| 门 | 防谁 | 判据 |
| --- | --- | --- |
| `authorizeHandshake` | 网络上的陌生人 | 握手 URL 的 `?token=` |
| `authorizeAdmin` | 已连上来的玩家 | `src='system'`（服务端内部）或持 admin token |

为什么 `save`/`load` 需要单独一道：`load` 会**整包覆盖权威 Sim**，任何连上来的陌生人都能回滚世界。
这正是 R1-2 要堵的口子，所以管理命令的放行面收紧到「服务端内部发起」与「持 admin token」两种。

比较 token 用定长循环而非 `===`：`===` 会在首个不同字节处短路返回，逐字节猜 token 成为理论可行
（时序侧信道）。JS 层拿不到真常数时间保证，但至少消除前缀短路。

### 8.4 R1-3 插值：红线是「不得污染逻辑状态」

`RemoteSim` 里现在有**两张表**，泾渭分明：

- `pawnMap` —— 服务端权威快照。命中判定、框选、HUD、`move` 命令的参数全部读它。
- `interpSlots` —— 渲染层双缓冲（prev/next）。**只有 renderer 读它**，通过 `WorldView.renderPos?()`。

**为什么不把插值塞进 `PawnState`**：

1. `PawnState` 是协议结构，往里塞渲染态会让服务端也被迫携带它（浪费带宽）且两端模型耦合；
2. 更要命的是，若 `pawns()` 也返回插值后的坐标，就会出现「看到的鼠」与「被选中的鼠」不是同一只——
   **批量指挥会指挥错对象**。插值只能是画出来的那一份，逻辑判定永远读权威值。

`renderPos?()` 在 `WorldView` 上是**可选方法**：联机的 `RemoteSim` 实现它，本地的 `LocalView` 不实现
（本地本来就是连续模拟，不需要插值）。renderer 用 `view.renderPos?.(eid, nowMs) ?? p.pos` 优雅降级，
于是渲染层对「本地/联机」依然零分支。

`k` 按 delta 间隔归一化而不是走固定步长：delta 间隔本身会抖动（拥塞时可能 1.2s 才来一帧），
固定步长会让插值在慢帧时「跑过头」——追上了下一帧目标又开始反向抖动。归一化后 `k` 恒在 [0,1]，
慢帧表现为**迟滞**（可接受）而非**越界抖动**（难看）。

`full` 到达直接 `snapTo`：全量对账帧代表「这才是事实」，插值它只会渲染出一个并不存在的中间位置。

### 8.5 R1-4 框选：手势重分配

左键从「拖拽平移」改为「画选框」——框选需要完整的按下-拖动-抬起手势，与左键平移无法共存。
平移因此迁到中键 / 右键 / 空格+左键。

其中**右键的语义推迟到 mouseup 才决定**：拖动过 = 平移，没拖 = 指挥移动。
如果按下就决定，右键单击（最高频操作）会被拖动判定误伤。

框选阈值 5px：低于它算单击点选，保住「点一下选中一只」的原有手感。
选框用**世界坐标**绘制而非屏幕坐标——相机一直在动，屏幕坐标的框会「粘」在屏幕上相对平移，
看起来像框跟着鼠标跑而不是框住世界。

### 8.6 R1-5 服务器存档：两个必须记住的坑

**坑一：`SERVER_COMMANDS` 白名单不登记 = 静默拒绝。**
服务端刻意不向客户端回显错误（避免暴露内部命令面），所以没登记的命令发出去**毫无反应**，
且 `rejectedCommands()` 只增不报错。R1-5 的 `save`/`load` 第一版就踩了这个坑。
凡是要上行的命令，必须同时做三件事：登记白名单 + 加参数校验 + 在处理器里实现。

**坑二：读档必须整包重建 `Sim` 实例，不能逐字段搬运。**
`rng` 内部状态、`nextEid`、`scratch`、各系统的闭包态都是实例私有的，逐字段搬运必然漏掉一部分；
漏一项的后果不是崩溃，而是「读档后行为慢慢分叉」——确定性续跑对拍失败，且极难定位。
重建实例是唯一能保证「读档后继续跑 ≡ 一直跑」的做法。
替换实例后还要给所有连接补发一帧 `full`：各连接的增量基准（`lastPawnJson`/`sentEvents`）已随旧实例失效。

**存档名必须过白名单正则 `^[A-Za-z0-9_-]{1,64}$`**：name 会直接拼进 `saves/<name>.json`，
放开 `.` 与 `\` 就是目录穿越。宁可拒绝玩家想要的中文名（可用性损失），也不要目录穿越（安全事故）。
`protocol.ts` 与 `save-store.ts` 各有一份实现，互为纵深防御。

## 从零重来 v3 · R2 阶段③补全：科技抽卡池与数据化部署（2026-08-21 追加）

> 上文 §9「分阶段落地」记录了阶段①~④的完成情况；阶段③（科技/数据化部署）当时被跳过，
> 由 ROADMAP R2 批次补上。本节追加其设计落点。

### 科技 = 独立抽卡池（碎片制）

蓝图原则⑤（保留条款）的落地形态：**解锁进度本身也是抽卡**。

```
科技池（全部科技，含已解锁）
        │ 每 intervalSec 抽一次，chance 决定是否发碎片
        ▼
按 TECH_ORDER 线性递减权重抽一项（rank0 权重最高 → 靠前的先攒齐）
        │ 抽到已解锁 = 重复卡，碎片不累计（稀释而非奖励）
        ▼
该科技碎片 +1 —— 攒满 fragments 自动解锁整卡 + 记事件
```

三条设计约束（互相咬合，缺一条就退化成别的游戏）：

1. **科技有自己的池子，与小人卡池完全解耦**。小人的抽卡决定「这 4 秒干什么」，
   科技池决定「世界解锁了什么」。两者共享 `ctx.rng()` 这一确定性随机源，但不共享候选集。
2. **神谕不能降下科技**（用户 2026-08-13 原话）。玩家的干预面仍然只有 move 基础指挥
   （见 AGENTS.md 用户裁定），科技进度**没有任何玩家可点开的按钮**。
   这与「策略卡 / ××令」机制被整体废除是同一条红线的两面。
3. **重复可开出**（用户 2026-08-15 裁决）。候选池含已解锁科技，抽到重复 = 稀释，
   让新科技解锁期望更慢 —— 渐进节奏由此自然产生，不需要额外的概率设计。

**权重为什么是线性递减而不是幂次**：n=4 时权重 4/3/2/1，靠前科技期望约 2.6 块就先攒齐，
靠后的要等前面的解锁完才轮得到。幂次会让靠后的科技在长局里几乎抽不到，
而线性权重的概率表能心算 —— 可解释性在这个系统里比曲线形状重要。

**门控是消费端，不是解锁端**：`BuildingTuningEntry.tech` 只是「建造前查一下这张表」，
解锁权始终在抽卡池手里。卸载 tech-pool 包 → 表空 → 门控一律放行 →
「永无科技但核心照跑」（原则④卸载不破坏核心）。

### .mod.json：数据化部署与「同一内容两种形态」

```
mods/*.mod.json  ──parse──►  ModPackageJson  ──modPackageToPack──►  ModPack
                                                                        │
src/mods/packs/*.ts ──────────────────────────────────────────────────►  ┤
                                                                        ▼
                                          topoSort → apply → validateContracts

                          （两条输入路径在这里合流，走完全相同的装配链路）
```

这个合流点是 R2-2/R2-3 的**全部意义**：数据驱动部署不是「另一条旁路」，
而是把内容翻译成同一个 `ModPack` 契约后复用既有装配器。
因此 JSON 作者与 TS 作者得到**逐字段等价**的装配结果，
区别只在作者用什么写（JSON 不能写函数，所以 TS 版多出谓词/系统/命令能力）。

**失败策略（响亮失败且绝不半挂载）**：

| 阶段 | 检查 | 失败时机 |
| --- | --- | --- |
| 解析 | JSON 合法性、`manifest` 形状、id 字符集 | 逐文件，带**文件名** |
| 拓扑 | `requires` 是否齐备、是否成环 | **挂载前** —— 调用方拿不到半成品 registry |
| 注册 | 重复 id、谓词名未登记、系列未登记 | 挂载中，抛错中止 |
| 契约 | `validateContracts` | 挂载后，视同失败抛错 |

拓扑检查刻意放在 `apply` 之前：旧加载器逐个挂载、挂到一半才发现依赖缺失，
留下的半挂载 registry 会让后续排查完全失去参照 —— 这是旧项目踩过的坑。

## 性能基准与记忆化（2026-10-06 追加，性能优化线）

### 为什么先有基准

本项目在旧实现阶段（`test/` 归档）做过 5 轮性能优化，其中「findNearest 空间索引」
实测**索引构建开销 > 节省**而被**回退**。能做出"回退"这个决定的前提是：手里
有"节省"这个数。性能线把这件事固化为 `scripts/bench.ts` + CI `perf bench` job。

三条设计约定：

1. **逐系统计时（`sysMs`）**：基准不只报一个总耗时，还要指出热点在哪个系统。
   没有这一段，任何优化都只能凭直觉猜——那正是旧项目"凭直觉改 → 改不动 →
   回头查为什么没收益"这条路的起点。
2. **玩法指纹**：基准输出 `alivePawns / events / usesTotal / stockFood /
   stockWood / buildings / techsUnlocked`。这些是确定性字段，**优化不得改变
   任何一项**；变了就说明「怎么算得快」被改成了「算出什么变了」，是回归。
3. **基准自己必须会失败**：加了自检（请求 `--pawns` 但出生鼠数不符即抛错）。
   起因是首轮 CI 的 6 组读数其实是同一组——参数解析让三个槽全吃到第一个 `900`，
   输出六行看起来正常的表。**假基准比没基准更糟**：没基准时你知道自己瞎，
   假基准给你自信的假数字，你会据此判断"优化有效"并写进 commit。

### 记忆化表（`src/sim/world.ts`）

四张记忆化表，统一遵循"**纯函数 + 容量封顶 + 整表清空**"约定（清空 = 重新推导，
确定性无损，与既有 `tileCache` 同款）：

| 表 | 键 | 被谁高频调用 | 为什么此前没缓存 |
|---|---|---|---|
| `tileCache` / `zCache` | `key2(x,y)` + 偏移 | 渲染 / A\* | （早就有，本轮沿用其编码约定） |
| `treeAnchorCache` | `key2(x,y)` + 偏移 | `canStep` → `canStand` → `treeBlockAt` → `treeAnchorAt` | 链尾是林地密度**值噪声**（4 次 `hash2`）；A\* 每展开一节点要对 8 邻域各调一次 = **每条边**重算。属"该缓存没缓存"的历史缺口 |
| `featureKindCache` | `key2(x,y)` + 偏移 | `nearestFeature` 环形扫描 | 半径 10 = 441 次/次调用，其中约 87% 返回 null 仍每次重算。且 `drawCard` 每次抽卡要为**每张卡的 condition** 各跑一次全环扫描 |

**键的偏移约定**：四张表都用 `key2(x,y) + 常量偏移` 区分键空间
（`+0 / +1e9 / +2e9 / +3e9`）。`key2(x,y) = (x+32768)*65536 + (y+32768)`，
在 `x,y ∈ [-32768, 32767]` 下最大约 `4.29e9`。

> ⚠ **为什么这个数字拼接是安全的**（知识库 `js-numeric-key-overflow` 记的正是同族坑）：
> 旧项目用 `key1 * 4194304 + key2`，坐标到几千时乘积就达 `1.8e19 > 9.007e15`
> （`MAX_SAFE_INTEGER`），key 静默碰撞 → 缓存返回"别人"的路径 → AI 走错路。
> 本式基数是 `65536`（不是 4194304）且坐标域被 `±32768` 夹住，最大值 `4.29e9`，
> 距上限有 **6 个数量级**余量；且它已是本文件 tile/z 缓存与寻路 `key()` 沿用的
> 既有编码。若将来放宽坐标域，必须重新核算这一条。

### 建筑 tag 倒排索引

`nearestBuildingByTag` 原是「线性扫全表 × 每座调 `tags.includes`」，而它是热路径：
`needs` 睡觉卡 action 每 tick 调 2 次（fire + shelter）、`gathering` 每次抽卡 1 次、
`building.wantNewFire` 更在"遍历每只鼠"的循环里逐鼠调（= O(鼠²) 次全表扫）。
现改为查 `tag → BuildingState[]` 倒排桶。

**与旧项目回退的那个"空间索引"有本质区别**，这是本轮敢做的判据：

| | 旧项目 findNearest 空间索引 | 本轮 tag 倒排 + 锚点表缓存 |
|---|---|---|
| 索引**构建**频率 | 每 tick 全量重建（×900 = 900 次） | 惰性增量：只在建筑增删时改一个桶（900 tick 里 7~14 次） |
| 调用密度 | 平均每 tick 仅 1.1 次环剪枝 | O(鼠 × tick) |
| 结论 | 构建开销 > 节省，**回退** | 读侧 O(1)，写侧极少 → 留 |

**一致性**：索引只在 `addBuilding` / `removeBuilding` / `importState` 三处维护，
`World.buildings` 也只在这三处变动，不存在"绕过索引改表"的路径。
`importState` 必须**整表重建**（`tagIndex.clear()` + 逐条 `pushIndex`）——
只对新增项增量维护会漏掉"清空"这一路，索引里留着已不存在的建筑（幽灵建筑）。

**⚠ 身份一致性**：`importState` 里必须索引**存进表的那一个对象**（先 clone 到局部
`b`，再 `buildings.set` + `pushIndex(b)` 同一个 `b`）。首版写成 `pushIndex(入参)`、
而表里存 `structuredClone(入参)`，导致倒排返回的对象与 `buildings` 表里那一座
不是同一引用——不抛异常，只表现为"按身份比较"时的偏差。已由 `perf-cache.test.ts`
的 ③b 用例锁住。

### Sim 侧的火堆锚点表缓存

`setPath` 原在**每次调用**都遍历全建筑表重建锚点数组 + 每座一个新对象分配，
而它是行为系统最热入口（采 / 砍 / 走 / 跑 / 睡五类卡动作都会调）。
锚点表是典型"**高频读 / 低频写**"：900 tick 里只变 7~14 次。
故缓存一份 + 用 `world.tagVersion()`（每次建筑增删 +1）判过期。

**桶序即原迭代序**：原实现 `for (b of buildings.values()) if (tags.includes('fire')) push(...)`
的顺序 = Map 插入序，倒排桶的顺序也是插入序。`planRoute` 对锚点做 `sort + slice(0,2)`
取最近两个，**并列时的胜出者依赖迭代序**——桶序一致，所以结果不变。

### `drawCard` 的复用缓冲

候选与权重数组改模块级复用缓冲。安全前提是**同步且非重入**：`drawCard` 内部只调
`condition` / `weightHooks` / `cardWeight`，而这些钩子的签名（`context.ts`）
只拿到 `(p, card, ctx)`，**没有抽卡面**，钩子里无法回调 `drawCard`。
⚠ 若将来允许钩子/谓词内重入抽卡，必须立刻改回局部数组，否则内层调用会踩掉
外层已写好的候选 = 抽到别的鼠的卡。

### 已知未修（登记而非顺手改）

`World.featureAt` 用**未取整**的 `x,y` 拼 `${x},${y}` 去查 `featureLeft`/`harvestCd`，
而 `takeOne` 用**取整后**的坐标。"这一格是什么特征"是对的（`featureKind` 内部取整），
但"这一格的余量/冷却"两张表在非整数坐标下会记到另一个键上。
修它会改变采收与再生的实际结果 → 改变玩法与平衡。本线硬约束是
「优化只能改怎么算得快，不能改算出什么」，故**单独立项**，不混进性能 PR。


### 读数纪律：为什么必须是配对 A/B（2026-10-06 追加）

**先记一条实测**：同一份代码、同一个 seed、同规格托管 runner，
两次 CI 运行分别报 `68.776ms` 与 `101.882ms` —— **差 48%**，其间零代码改动。

托管 runner 是共享虚拟机，同机邻居、CPU 频率调度、steal time 全不可控。
所以：

> ❌ 拿两次不同运行的读数相减 → 得到的是噪声，不是收益。
> ✅ 必须让「优化前」「优化后」两棵代码树在**同一台机器、同一个 job 里交替**采样。

`scripts/ab-bench.sh` 的设计要点：

1. **两棵真实代码树**，不是运行时开关。`git worktree` 拉出基线 ref。
   理由：内核里写 `if (AB) 旧路径 else 新路径` 会让 V8 同时编译两条路径、
   两条路径 JIT 成熟度不同，测出的差值混着测量本身的偏差；更糟的是
   **分支预测器会记住上一轮走哪边**，交替采样时反而引入新的偏差。
2. **交替 A B A B**，取中位数。共享 runner 的漂移随时间缓慢变化，
   交替采样让两条臂吃到几乎相同的漂移。
3. **噪声地板**：报告每臂的极差，并显式给出判语——
   差值必须**大于**噪声地板才算信号，否则结论是"本配置测不出收益"，
   而不是"大概快了一点"。
4. **先判红线**：玩法指纹（alivePawns/hostiles/buildings/events/usesTotal/
   stockFood/stockWood/techsUnlocked）跨两臂/多轮只要不一致，立即退出并报
   「这是回归不是优化」。性能数字再好看也不能掩盖玩法分叉。

实测效果：噪声地板从"跨运行 ±40%"降到"**同机交替 ±4%**"，
原本测不出的差异变得可判定。

> 这条本身就是本项目的一条通用纪律（已写入 PROGRESS.md）：
> **没有配对基准的优化，连"有没有变快"都不知道。**
## 分区块同步（line/net，2026-10-06）

### 为什么不改地形模型

任务书提到"存档按区块存/取，接上 `serializeChunks()` 的 diff 思路"，归档旧实现里
那套是**双图层**：生成层 `ensureChunk` 存 Uint8Array + 覆盖层 `overlay: Map<chunkKey, Map<offset, tileIndex>>`。
**本轮刻意没有照搬。** 理由：v3 的地形是**纯函数派生**（fractal 高度 + per-tile z
+ value-noise 森林密度 + tile memoize），且**玩家不能改写地形**（砍树只加冷却，
不改 tile）。生成层的价值只在"地形会被写"时成立；套到纯派生地形上，
会把 O(1) 空间变成 O(已访问面积) —— 是**性能倒退**，不是优化。

所以本轮只在**实体状态**上加了派生的区块索引（惰性建 + 增量维护，真源表仍是唯一事实）。
**判错的推翻路径**：一旦出现改写地形的玩法路径（挖地基 / 填湖 / 建造压平），
立刻回到双图层，因为那时"生成层 + 覆盖层"才是对的抽象。

### 键解码纪律，以及一个"防御反而是 bug"的实例

2026-08-14 踩过：17 处内联 `k % width` 漏改，症状是**桥不修/篝火不迁/伤口不疗**的
沉默损坏。本轮所有区块键解码收口到 `chunkKeyToXY` 唯一入口。

但本轮 CI 抓到的恰恰是"防御代码"自己出事，值得完整记下：

```ts
// 第一版（照抄旧实现的防御思路）
let cx = key % SPAN; let cy = Math.floor(key / SPAN);
if (cx > SPAN / 2) { cx -= SPAN; cy += 1 }   // ← 凭空造 bug
```
实测 `chunkKey(1, 1)` 解出 `{cx: -65535, cy: 2}`。

**根因**：`chunkKey` 给两个分量都加了 `CHUNK_KEY_BIAS = 32768` 偏置，所以
`key ≥ 0`，而**非负数的 `%` 恒在 [0, SPAN)**——`cx + 32768` 天然就在合法区间里，
**根本不存在需要回拨的负余数**。那个 `cx > SPAN/2` 分支不是防御，是把合法的
`cx=1`（余数 32769 > 32768）当成"偏移过的负余数"拉了回去。

**教训（比代码本身更重要）**：负坐标的坑不在"要不要回拨"，而在**"你的编码是否自带偏置"**。
带偏置的加法编码里 `%` 恒安全；不带偏置的编码里 `%` 才是截断余数陷阱。
**照抄防御代码而不验证它在自己编码下是否成立，比不写防御更危险** —— 后者至少是
可见的缺口，前者制造的是"看起来很严谨但恒错"的代码，只有**穷举**测试能抓住
（所以 chunk-geom 对 7×7 邻域穷举往返，而不是手挑几个样例）。

### tick 不按"预算"切多帧，而按"区块集合"缩小工作集

任务书说的是 budget 分片。**这里选了"按区块决定工作集、预算=工作集大小"**，
理由：模拟时间必须**等距推进**才能让远端客户端插值对齐（`interp.ts` 按 delta
间隔归一化 k）。把一个 tick 的工作摊到后续 tick，会让某些 tick 的 `dt ≠ 0.1`，
破坏插值手感与所有"每秒速率"的确定性。

诚实边界（实测见 PROGRESS）：**分片收益与"被跳过区块里的实体数"成正比，与总实体数无关**。
首轮基准 4 只鼠全在一个块里时，`sparse` 比 `null` **还慢 0.0028ms** —— 纯粹多付了
Set 查表的常数开销。鼠分散到 9 块后才是 4.31×。

### 两个必须破例的保功能点

1. **被选中 / holdUntil 中的鼠出 scope 仍下发**。否则"框选后指挥"会发给空气。
2. **出 scope 的 pawn 要从 `lastPawnJson` 基线里删掉**。否则走回旧区块时，
   它与基线逐位相同 → 被判定"无变化"而漏发 → 玩家回到原地发现鼠不见了。

另外 `droppedChunks` 是**必需的卸载信号**，而 `delta.scope` **明确不是**：
delta 的 scope 语义是"变化**可能**在这里"，用它当卸载依据会把"这帧没动静"误读成"该卸载"。
