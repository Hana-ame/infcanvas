# infcanvas 设计文档

> 2026-08-03 · 从 gsap-framework 拆出的独立项目

## 0. 北极星（north star）

**这个游戏的最高目标 = 模拟一个现实的社会。**

一切机制（自主 AI、神谕信仰、意图失真、工厂物流、派系战争、亚空间）
都是手段，都在为"让一个虚拟社会真实地自己运转"服务。
设计取舍时用这个问题来检验：**这样做是让社会更真实，还是只是更像游戏？**

## 1. 定位与核心概念

**一句话：模拟一个现实社会的实时模拟——RimWorld 的地块深度 + Dwarf-Fortress 的自主小人 + 工厂物流链（戴森球计划式）+ 玩家不是指挥官而是神谕。**

玩家**不逐个指挥小人**。小人有自己的目标（由 LLM + 确定性 AI 驱动），
玩家在**特定条件下影响小人的目标层**，让小人目标随玩家而动——玩家是改变世界的力场，
不是遥控器。

| 项 | 决定 |
|---|---|
| 类型 | 现实社会模拟（自主文明 + 神谕干预） |
| 渲染 | infinite canvas：世界 = 单张连续地图 canvas/WebGL(Pixi)，UI = DOM |
| 时间 | 纯即时（不可暂停，可选倍速），观察演化 |
| 联机 | 是（最终目标），WSS（专用服务器） |
| LLM | 小人目标决策 + 野生神谕 + 事件生成 + 建筑/城镇/工厂规划 |
| 插件 | mod：新增物品、新 AI、新事件、新建筑、新神谕能力 |
| 玩家角色 | 神谕（oracle）：通过教堂影响来教堂的人 |
| 目标 | 纯沙盒，无胜负 |
| 玩家身份 | 可切换：先以个体小人扮演，也可转为神谕 |
| 世界 | 单张连续地图（infinite canvas），相机任意平移缩放 |

## 2. 核心张力：意图失真（intent loss）

**游戏的根本张力 = 玩家想影响世界，但世界不完全听你的。**

玩家与小人之间存在三层信息损耗，这是玩法核心而非缺陷：

```
玩家意图 ──【LLM 理解偏差】──▶ 神谕表达 ──【小人个体利益过滤】──▶ 实际行为
```

1. **LLM 理解偏差**：神谕 → LLM → 意图，LLM 特性决定了它不能 100% 理解玩家意图（这是 LLM 固有特性，不是 bug，是风味）
2. **小人个体利益**：玩家的利益 ≠ 小人的利益。小人有个体利益、性格、信仰，可能不执行甚至违背神谕
3. **信息盲区**：亚空间等区域玩家完全不可见，只能靠预置指令间接影响

> "玩家和 LLM 斗智斗勇" = 上述链路自然产生的博弈，不是刻意的对抗设计。

## 3. 玩家 = 神谕（oracle）交互模型

```
RimWorld:   玩家 ——点选→ 小人执行具体命令（去采矿、去建造）
infcanvas:  玩家 ——施加影响→ 小人目标层 → 小人自主决定怎么执行
```

- 玩家对某个小人/派系施加"神谕影响"（祝福、指引、警告、启示）
- 神谕影响进入 **LLM 慢决策层的上下文**，改变小人的 long-term goal
- 微观执行（怎么走路、什么时候吃饭）永远由确定性 AI 完成
- 玩家不是无能为力：神谕影响够强就能改变小人的路线，但小人仍是自主的

### 神谕影响范围：影响圈 + 来教堂的行为选择

- **影响圈 = 教堂的吸引力范围**：只在影响圈内，小人的卡池才出现"参拜"这张卡（或参拜卡权重受距离调制——越近权重越高）
- **来教堂 = 一个行为选择，走抽卡机制**（宗教系列卡）：抽 3 选 1 时，参拜 vs 干活的**收益对比**决定来不来
- **太忙不会来**：忙人的参拜收益低（状态/收益调制），干活卡收益压过参拜——神谕影响力 = 教堂吸引力 × 小人空闲度 × 信任度
- 常来教堂的小人受神谕影响更深（信任度累积），从不来的人不受影响
- 这让神谕有**地理性 + 时间性**：玩家要影响一个忙碌的社会，要么让教堂更吸引人（布道/仪式/信物），要么等他们闲下来
- 待定：神谕是"单个小人"级还是"派系/城镇"级

### 玩家身份可切换

- **开局**：可以扮演一个具体小人，或直接扮演神谕
- **随游戏进程**：扮演的小人可以创建宗教/成为神谕；神谕也可选中某小人使其单独收到"指挥"
- 视角身份是连续的，不是两个割裂模式

### 神谕通过教堂发布（核心约束）

神谕**不能凭空施法**——神谕影响必须通过**神庙/教堂**这个物理实体发布：

- 玩家必须先让小人建造教堂，神谕才能在教堂发布影响
- 神谕只能在教堂"降下"，教堂是神谕与世界的唯一物理接口
- 不同教堂可传播不同教义，玩家可建立多个教堂网络
- 教堂是世界可见的建筑，可被异教派系**毁坏**（信仰博弈的物理表现）
- **亚空间里不准建教堂**（亚空间不可见，神谕影响力无法触及）

### 野生神谕（AI 神谕）

**神谕不只有玩家。** LLM 会扮演天然的野生神谕（"分发神谕的天然 AI"），
它们拥有自己的教堂、信誉度，并主动传教：

- 野生神谕自主建立教堂，向小人发布影响，与小人的利益/派系互动
- 玩家神谕与野生神谕**竞争信徒**——同一批小人的信任度会被多个神谕争夺
- 这是"玩家 vs LLM 斗智斗勇"的核心：不只是玩家影响世界，还有 LLM 神谕在影响世界
- 玩家可能让小人"改信"自己的教堂，也可能被野生神谕抢走信徒

### 教堂怎么建立

- 小人自主建（受神谕引导后自主决定）——默认路径
- 神谕玩家引导建（间接，神谕决定建在哪）——玩家路径
- 两种都存在，同一世界里共存

### 信誉度 + 信任度（双维度信仰系统）

| 维度 | 含义 | 机制 |
|---|---|---|
| 神谕信誉度 | 玩家作为神谕的长期声望 | 发布准确的指引（让小人受益）→ 涨；发布误导/虚假指引 → 跌 |
| 教堂信任度 | 单个小人/派系对**某个教堂**的信任 | 每个教堂独立累积；小人受该教堂神谕影响的能力 = 信任度决定 |

- 小人会对某个教堂的神谕产生**信任或不信任**——信任度低的小人可能无视该教堂的神谕
- 信仰博弈：同一神谕在不同教堂发布，效果因小人对各教堂信任度而异
- 信誉度高 → 小人更愿意建教堂/追随；信誉度低 → 神谕逐渐失去影响力
- 这是"玩家利益 ≠ 小人利益"的又一体现：小人可以不信，信仰是争取得来的

### 小人可编程：插槽系统（同源机制）

**小人是可以被编程的**——信仰足够高时，神谕可以为小人设置行为逻辑。
L258 原则成立：**行为指令集不经过 LLM，确定性概率执行**，LLM 只控制概率。

#### 插槽系统（类似 DNA/天赋槽）

每个小人身上有固定数量的**插槽**，神谕把行为指令"插"进去：

- **槽位数量**：天生固定槽数 + 可解锁潜能槽（信越深/成长越多槽）
- **可替换**：槽内指令可换，但**更换需要走事件**（不是随时改）
- **凹小人**：玩家通过筛选小人（天生槽数/属性）+ 后天培养，凑出理想配置
- **DNA/天赋 = 天赋卡**：小人生成时由 DNA 决定，以**天赋卡**形式占用槽位（被动修正卡：天生蛮力、夜猫子体质、心灵手巧）；DNA 同时决定槽位数量与布局——DNA 是底子，槽位 + 天赋卡是它的表现
- **统一卡模型**：天赋卡 / 技能卡 / 习惯卡 / 神谕策略卡都是同一种卡，区别只在来源与可否移除：

  | 卡来源 | 谁给 | 可否移除 | 例 |
  |---|---|---|---|
  | 天赋卡 | DNA（生成固定） | 不可（或极难，走事件） | 天生蛮力、夜猫子体质 |
  | 技能卡 | 学习/练习 | 可（遗忘退化） | 射箭熟练 |
  | 习惯卡 | 反复行为养成 | 可（改不掉的老毛病） | 酗酒、早起 |
  | 神谕策略卡 | 信仰解锁插入 | 可（换槽走事件） | 白天传教、入夜警戒 |

- **槽内容两类**：
  1. **下一个目标选项**（带触发权重）——小人的"下一个目标"从插槽中按权重挑选
  2. **行为规则**（`当 X 时 → 做 Y`）——触发式行为约束

#### LLM 只印卡和触发事件（不碰选择过程）

**LLM 完全不进入行为选择链路**，只有两个职责：

1. **印卡**：创建/插入新卡（神谕策略卡、野生神谕的卡、事件奖励的卡）——LLM 生成卡的内容和初始权重，之后选择过程与 LLM 无关
2. **触发事件**：事件通过**统一接口调整卡的权重/收益**（"村外发现矿脉"事件 → 挖矿卡权重 +50）——LLM 只改世界，不改小人

- 行为选择的权重调整全由确定性机制完成（环境/状态/事件/性格）
- LLM 零延迟零成本压力：印卡和事件都是低频、异步、批量可做
- 意图失真保留：LLM 印的卡要小人信任才进槽（信仰/信任度过滤）

#### 事件触发 = 状况匹配的事件列表（不写死）

事件系统是**数据驱动的事件列表**，系统每轮从"符合当前状况"的列表里选事件，不把触发逻辑写死在代码里：

- 每个事件 = `condition(ctx)`（**状况匹配**：只有当前局面满足才进候选池）+ 效果（改资源/建单位/调卡权重/记历史）
- 例：有农田才"丰收"、有余粮才收留"流浪者"、开过矿洞才"发现矿脉"、人口≥3 才可能"瘟疫"、有物资才"游商到访"、整体低落才"庆典"
- 候选池再叠加 `weight`（权重）/ `cooldown`（冷却）/ `minTime`（开 X 秒后可触发）调制
- **LLM 接入点 = provider 可插换**：P0 用确定性脚本列表；P1 把 provider 换成 LLM 生成的事件（同一 `ScriptedEvent` 接口），LLM 只印卡 + 触发事件，不进选择链路

#### 执行模型（抽卡，无合成器）

```
小人 DNA（生成时固定）→ 决定天赋 + 槽位数 + 槽位布局
        ↓
卡池 = 基础卡 + 天赋卡 + 技能卡/习惯卡 + 神谕策略卡(信仰过滤)
        ↓
定时 check: 按权重抽 3 张（不放回，种子化）
        ↓
3 张中挑收益最高的执行（收益表每日重算一次）
        ↓
生成 job → 事件 → COC 骰子判定 → 结果 → 日志 / 熟练度 / 权重调整
```

- **与亚空间预置指令同源**：亚空间航行中玩家无法实时指挥，同一套插槽/指令系统 = 唯一控制方式
- **意图失真保留**：概率不是 100%，小人本性可违抗，但高信仰 + 凹好的插槽可接近"编程感"
- 这是"信仰 = 控制权"的落点：信仰累积到足够高 → 解锁插槽 → 编程小人行为

### 神谕资源的约束

- 神谕影响不能无限用（防止变成变相遥控器）
- 机制候选：冷却时间 / 信仰值（信仰越足，影响越强）/ 影响力点
- 待定：神谕是"单个小人"级还是"派系/城镇"级

### 神谕的情报流：拒绝全知

神谕的信息**不能来自上帝视角**，只能来自教区情报流：

- 情报来源 = 教堂/祭司视角的观察：报告、传言、信件、人口统计——滞后、片面、可能失真
- **未建教堂的区域 = 盲区**（与亚空间同类），神谕不知道那里发生了什么，只能间接影响
- 情报失真成为机制：传言会变形（参考 DF 传闻系统），祭司可能隐瞒或夸大
- 盲区是世界显得"独立于玩家"的第一手段；全知 + 无约束干预 = 变相遥控器（WorldBox 教训）

### 历史系统：仿真日志（Legends 式）

历史不是"事后编的故事"，而是**仿真日志**：

- 每次确定性事件结构化记录：实体、地点、时间、因果链（谁对谁做了什么）
- 事件系统是一等公民：可查询、可导出、可回放（DF Legends 可导出千年历史）
- **LLM 只做叙述润色**（把日志写成编年史/歌谣），不产生事实——事实只能来自 sim
- 世界生成时先跑"零玩家策略游戏"：seed 生成地形后确定性模拟数百年历史，玩家开局看到的废墟、旧战场、仇敌关系全部来自这段仿真，而非随机点缀（Qud 历史生成的约束满足思想：每片区域至少被提及一次，事件不能与已有历史矛盾）
- 历史是神谕的感知窗口之一（与情报流互补：历史是全的但可能没人告诉你）

## 3. 世界模型：多派系自主文明

AI 不止管一个殖民地——小人在世界各处自主建镇、扩张、互相战争：

```
世界（infinite canvas，分块生成）
 ├─ 派系 A   ── 城镇 ├─ 建筑 ── 居民（pawn）
 │                   └─ 首领（LLM 决策）
 ├─ 派系 B   ── 城镇 ── ...
 └─ 无派系群体（流浪者、野人营地）
```

- **派系关系**：友好/中立/敌对，随事件与战争演化
- **城镇**：AI 规划选址、扩张、建造（选址 = LLM 慢决策，施工 = job 系统确定性执行）
- **战争**：派系间攻防（目标 = LLM 决策，战斗/行军 = 确定性 AI）
- 玩家可以有自己的"信徒派系"，也可以只当旁观神谕

### 小人的欲望系统（利益驱动 + 经济咬合）

**经济系统的意义 = 满足小人的欲望，不是抽象 GDP。小人利益 = 欲望满足程度。**（意图失真的机制层落点：小人的利益 ≠ 玩家的利益）

**欲望结构（checkpoint 机制）**：

- **欲望类型 = 七宗罪**（中世纪神学框架，与神谕/教堂主题同构）：

  | 罪 | 驱动行为 | 满足方式 |
  |---|---|---|
  | 暴食 gluttony | 进食、享乐 | 食物、酒宴 |
  | 懒惰 sloth | 逃避工作 | 休息、清闲 |
  | 贪婪 greed | 囤积 | 财产、资源占有 |
  | 嫉妒 envy | 攀比 | 相对地位、压过他人 |
  | 傲慢 pride | 被尊重 | 声望、头衔、崇拜 |
  | 暴怒 wrath | 攻击 | 发泄、暴力胜利 |
  | 色欲 lust | 繁衍 | 伴侣关系 |

- 每个小人**先天有罪孽倾向**（性格权重：天生暴怒者 vs 天生谦和者），环境与事件改变后天权重
- **七美德（谦卑/慷慨/贞洁/耐心/节制/勤奋/慈善）是对立轴**——教堂宣扬美德，小人天然倾向罪孽，信仰系统因此有道德维度
- 每个欲望有**数个 checkpoint**（阈值分档）：满足 → 勉强 → 匮乏 → 危急
- **定期检查**（非每 tick——欲望变化慢，检查也慢，每隔一段时间运行一次，比对已有资源/环境是否满足欲望）
- 检查结果驱动行为权重偏移：需求未满足的欲望在 job 选择中权重升高

**每日记录**：

- 每天把满足程度写入"欲望满足史"
- 满足史进三层记忆（暗记忆凝练为"长期不满"等印象），影响 LLM 对小人心理状态的判断

**不满足的后果（梯度行为变化）**：

| 档位 | 行为 |
|---|---|
| 轻微不满 | job 选择权重偏移，优先做满足欲望的事 |
| 中等不满 | 个人需求 job 抢占派系 job（DF 式高优先级需求，不可取消） |
| 严重不满 | 行为模式变化 + LLM 决策上下文注入"不满"状态（过激倾向） |
| 恶意槽激活 | 长期不满足累积恶意计数器，达阈值激活**恶意槽**：反社会行为——偷窃、抢劫、暗算、背叛、参与叛乱 |

- 恶意槽 = 意图失真的极端表现：神谕要他虔诚，他饿肚子就会去偷
- **恶意槽 = 罪孽累积**：长期不满足的罪孽把行为推向该罪的过激形态——暴怒→暴力、贪婪→偷窃抢劫、嫉妒→暗算背叛、傲慢→暴政；罪孽累积进恶意槽，达阈值激活反社会行为
- 参考：Songs of Syx 死亡螺旋（资源短缺→不满连锁→暴动→崩溃）、DF 需求 job 抢占、CK3 阴谋/压力系统

**与经济系统的咬合**：

- 欲望满足需要经济资源（食物/住房/工具/奢侈品），经济瓶颈 → 欲望不满 → 行为变化 → 社会动荡
- 资源短缺是小范围的（某个镇缺粮），不满就是局部的——欲望系统天然产生区域性社会压力

**与神谕的关系**（干预杠杆，不违反"不直接指挥"）：

- **纵容型影响**：满足罪孽（赐酒宴、纵容复仇、赏财富）——见效快，但长期腐蚀社会（B&W 教训：邪恶路线快而毁）
- **美德型影响**：导向美德（布道压制罪孽权重、宣扬七美德）——慢、可持续，但压抑可能反弹（欲望越压越烈）
- 重塑型影响：改变欲望权重（贫困时引导转向信仰，"富人靠科技穷人靠神"），不动经济只动欲望结构
- 七宗罪 × 七美德的轴心让神谕的每次干预都有道德代价——选择纵容还是压抑，本身就是世界叙事

### 小人的属性与骰子判定（COC 式角色卡）

**每个小人 = 一张 COC 式角色卡。骰子不裁决动作，裁决事件成败**——决策链：

```
触发决策(欲望checkpoint / LLM意图 / job) → 决策 → 生成执行事件 → 骰子裁决事件成败 → 结果入日志
```

- 骰子只出现在"决策之后、事件落定之前"，不做动作级判定（走路/吃饭不掷骰）
- 事件失败 → 进恶意槽/事件素材；确定性实现：骰子 = 种子 RNG 封装（`SimRng.d100()`），回放可复现

**属性卡**（COC 八属性）：

| 属性 | 含义 | 影响 |
|---|---|---|
| STR 力量 | 体力 | 近战、搬运、建造 |
| CON 体质 | 健康 | HP、抗病 |
| SIZ 体型 | 体格 | HP、负重 |
| DEX 敏捷 | 灵活 | 闪避、命中、手工 |
| APP 外貌 | 魅力 | 社交、信仰传播 |
| INT 智力 | 思维 | 技能学习、施工精度 |
| POW 意志 | 精神 | **对抗欲望**、抗压、SAN 上限 |
| EDU 教育 | 知识 | 技能起点、科技 |

**技能**：百分制（1-100），工作/社交/战斗/感知四类，由 defs 注册（mod 可加新技能）。

**判定**（掷 d100 对抗技能/属性值，成功度分级）：

| 掷骰结果 | 等级 | 后果 |
|---|---|---|
| ≤ 技能值 | 成功 | 正常效果 |
| ≤ 技能值/2 | 困难成功 | 更优效果 |
| ≤ 技能值/5 | 极限成功 | 最佳效果 |
| 01-05 | 大成功 | 暴击，超出预期 |
| 96-100 | 大失败 | 灾难 → 进恶意槽/事件素材 |

- **对抗检定**：双方事件冲突时各自掷骰比成功度（战斗、说服、偷窃、传教）
- **只对有风险、有意义的事件掷骰**（COC 原则）：骰的是攻击事件、技能使用事件、社交对抗、危险行动，不是日常行为
- **确定性实现**：骰子 = 种子 RNG 封装（`SimRng.d100()`），结果记录进"历史=仿真日志"（谁对谁掷了什么），LLM 只润色叙述（"他这一剑几乎劈开了甲胄"）——AI Roguelite 同构：LLM 决策 + 骰子裁决，数值永远在引擎侧

**POW 对抗欲望**（与七宗罪系统咬合）：

- 压抑罪孽 = POW 检定：失败 → 当场冲动满足罪孽（暴怒者挥拳、贪婪者顺手牵羊）
- 长期压抑失败累积 → 恶意槽；POW 高的圣人 vs POW 低的凡人——**美德修行本质是 POW 训练**
- 神谕的布道/祝福可临时提升 POW 检定（美德型干预的机制落点）

**SAN 理智**（对接创伤记忆）：

- 目睹死亡/恐怖/疯狂事件 → SAN 下降；低 SAN → 狂乱发作（短期疯癫行为：跑走/发呆/攻击），是"行为变化"的极端档
- 恢复途径：休息、教堂告解（神谕的干预杠杆）；SAN 永久损伤 → 长时记忆固化（DF 创伤记忆的 COC 化）

**技能成长**（COC 经验规则）：

- 使用技能后掷 d100，> 当前值则 +1d10——越用越强，边际递减
- 小人的"人生" = 技能曲线 + 欲望史 + 记忆，全进三层记忆的暗记忆凝练

**战斗流程**：

```
LLM 定战略意图(进攻/包围/撤退) → 确定性层移动/接敌 → 生成攻击事件 → 骰子裁决事件成败 → 结果入日志
```

- LLM 永远不掷骰、不算伤害；骰子只在事件层裁决（避免骰子风暴）
- mod 接口：新技能/新属性 defs 注册、判定钩子（自定义检定规则）

### 空间模型：亚坐标精度 + 区块系统

**混合精度模型（Factorio 式，非 RimWorld 全贴格、非全连续）**：

| 保持 tile 格子的（逻辑层） | 连续 float 的（物理层） |
|---|---|
| 地形类型 / 可走性 / 资源分布 per-tile | 实体位置（世界单位） |
| **建筑 footprint 贴格** | 碰撞 = 圆形半径（≈0.3 格） |
| chunk 划分 / 生成 / 流式 / 持久化 | 移动轨迹、速度 |
| 寻路图（nav grid = tile，不细化） | 交互距离（工作点偏移，非贴邻格） |

- 地形/建筑必须贴格：生成、覆盖层、寻路可走性、流式全依赖格子，全连续则"资源在哪/墙挡路没"都要浮点几何判断
- 实体连续：pawn 不跳格，工作站在目标旁的任意偏移点（如砍树站在 `(3.5, 4.2)`）
- 碰撞发生在建筑边界（线段/矩形 vs 圆），墙格在寻路图中标记不可走

**坐标系约定**：

```
世界单位(float, 权威) ──/tileSize──► tile 坐标(int) ──/chunkTiles──► chunk 坐标(int, 可负)
```

- 逻辑运算（寻路、footprint、资源判定）用 tile；物理运算（移动、碰撞、距离）用世界单位；权威永远是世界单位
- chunk 键为整数对（支持负坐标），实体坐标以整数 tile 为权威，渲染坐标派生（浮点漂移只影响画面）

**移动链路**（分层不变，执行变连续）：

```
目标点 ─► grid A*(tile 可走性) ─► 路径点列表 ─► 连续寻迹 + 避让(steering) ─► 平滑位置
```

**区块系统：双图层模型**

无限地图不可能全量存储，chunk 拆两层：

```
chunk(64×64 tile) = 生成层(确定性地形, 不落盘) + 覆盖层(玩家/AI 改动, 才存储)
                         ↑                              ↑
        seededRng(chunkX, chunkY) 即得           建筑/采空资源/道路 = 与生成层的差异
        任何人重生成结果一致                        覆盖层才需要持久化和网络传输
```

- **活跃半径**：只有玩家/派系附近的 chunk 参与 tick，远的休眠（不 tick、不占内存）——同时解决 sim 性能、内存上限、网络流式范围
- **流式协议**（消息形状现在定，P2 实现）：`S→C: chunkData { x, y, terrain[], entities[], defsRev }`；`C→S: watchArea { center, radius }`（客户端报视口，服务端决定发什么）
- **实体驱逐语义**：实体不随 chunk 驱逐——`entityId → chunkId` 索引保持，chunk 卸载只丢地形数组，实体列表单独驻留或序列化进覆盖层
- **P0 范围**：种子确定性生成（惰性 getChunk(x,y)）、稀疏存储 + 负坐标、客户端按视口加载/卸载渲染对象、双图层数据结构（覆盖层先放内存 Map）
- **留待 P2**：覆盖层持久化/落盘、休眠驱逐（活跃半径模型）、压缩传输、watchArea

**亚坐标带来的连带变化**：

- **空间索引**：chunk 内挂 spatial hash（bucket ≈ 1 tile），碰撞查询取本 chunk + 邻居 chunk 的索引，chunk 边界无感
- **job 到达判定**：`distance < workRadius`（float 比较），workRadius 是 def 数据而非写死"两格相邻"
- **确定性**：浮点在单机服务端上确定性成立（同输入同顺序同结果），回放复现依然成立；跨机器确定性已放弃（server-authoritative）
- **渲染**：连续位置让客户端插值更平滑

## 5. 权威模型：server-authoritative（TS 双端共用）

- **权威仿真 = TS sim**，P0 单机跑浏览器内，P1 联机跑 Node server（20Hz tick），客户端渲染（60fps）+ 插值
- **sim 逻辑一份，双端复用**——P1 时 server 直接 import `src/sim`，无双写成本
- 锁步确定性同步放弃（AI 复杂、浮点非确定）；但 **roll/骰子用种子化 RNG**（回放可复现）
- 客户端只发命令（move/build/harvest + 神谕影响），服务端校验后执行
- **分块生成**：server 生成 chunk 流式下发，server 是唯一事实源

### ECS：sim 的核心架构

**ECS 是必须的**——它是整个 sim 的地基，双端共用（P0 浏览器 / P1 Node server 同一套）。

- **方案**：bitecs（TS 最成熟的纯数据 ECS，零依赖，序列化友好，联机同步天然契合）
- **SoA 布局**：组件存数组而非对象，实体 = id，系统按数组批量遍历
- **确定性**：系统顺序固定 + 种子化 RNG（SimRng），同输入同顺序同结果，回放可复现
- **序列化**：ECS 纯数据 → 快照/增量同步直接用结构化数据，P1 联机消息不卡壳
- **SIMD 化（后续）**：TS 可用 WebAssembly/SIMD 加速批量系统，P0 不需要，P3 性能优化再上

### LLM 与权威模型

- **LLM 决策必须在服务端执行**——多客户端各自调 LLM 会状态分叉，破坏一致性
- 客户端不持有 API key，只接收 LLM 决策结果（作为正常 sim 更新）
- 服务端 LLM 网关：排队、超时、重试、成本控制
- LLM 决策结果 = 印卡 + 事件（详见 §6 决策模型），作为正常 sim 更新注入，行为选择 100% 确定性

## 6. 决策结构（LLM 关键设计）

LLM 延迟是秒级，游戏 tick 是 20Hz。分层，LLM 永远不进主循环：

```
┌─────────────────────────────────────────────┐
│ 神谕输入（玩家）◄──────────────────────────── │
└──────────────────────┬──────────────────────┘
┌──────────────────────▼──────────────────────┐
│ 慢决策层（LLM，异步，秒级）                    │
│   · 小人 long-term goal（受神谕影响）          │
│   · 派系决策（建镇选址/扩张/宣战/外交）          │
│   · 事件生成（流浪者/灾害/商队/奇遇）            │
│   · 只印卡 + 触发事件，不碰行为选择            │
├─────────────────────────────────────────────┤
│ 快决策层（确定性 AI，20Hz）                   │
│   · 抽卡选择 / 寻路 / job 执行 / 战斗          │
│   · 完全确定性，无 IO，离线可跑                 │
├─────────────────────────────────────────────┤
│ sim 核心（确定性，20Hz）                      │
└─────────────────────────────────────────────┘
```

- LLM 输出 = 结构化**卡/事件**（印新卡、触发事件改权重/收益），不产生决策、不碰选择链路
- 微观行为（抽卡、寻路、施工）永远是确定性 AI，不经过 LLM
- pawn 等待 LLM 回复时挂起在"思考"状态，不阻塞世界
- **神谕 = LLM 印卡的来源之一**：神谕策略卡由 LLM 生成内容，经信仰/信任度过滤后进卡池
- **行为指令集（神谕编程）不经过 LLM**：预设指令 + 抽卡执行是确定性系统，LLM 只负责卡的存在与事件

### 决策模型：抽 3 选 1（无合成器）

行为选择没有合成器——**权重抽卡 + 收益择优**：

```
卡池(基础卡 + 天赋卡 + 技能/习惯卡 + 神谕策略卡)
        │ 定时 check(每 0.5 游戏日 / job 完成)
        ▼
按权重抽 3 张(不放回, 种子化) ──► 收益表(每日重算一次) ──► 挑收益最高的一张
        │
   生成 job → 事件 → 判定(COC骰子) → 结果 → 日志 / 熟练度 / 权重调整
```

- **权重 = 冲动**（性格 / 习惯 / 环境 / 状态 / 事件调整）——决定**抽到哪些卡**
- **收益 = 理性**（局势评估：饥饿 → 吃收益高；矿脉事件 → 挖矿收益高）——决定**选哪张**
- 权重与收益分离：冲动小人抽到歪卡但收益理性仍会选对的；被事件/教义大改权重时可能 3 张全歪
- **收益每日重算一次**（1day1次，低频）：性能友好 + 局势变化不会让小人秒变卦
- **LLM 完全不碰这里**：只印卡（改变卡池）+ 触发事件（事件调权重/收益），选择链路 100% 确定性
- **可读性**：神谕能看到小人"闪过哪 3 个念头、选了哪个"——狗屁倒灶日志的素材
- 违抗 = 可选的附加 roll：3 张里若欲望卡（七宗罪临时卡）被抽到但收益低没被选 → 违抗 roll 改选欲望卡
- 同输入同输出：抽卡与收益都是纯函数（种子化），回放可复现

#### 插槽系统：槽位 + 策略卡（完整版，P0 实现规范）

**总体结构**：

```
DNA(生成固定) → 槽位布局 + 天赋卡
                    ↓
槽位(类型/容量/优先级) ← 装载卡(天赋/技能/习惯/神谕)
                    ↓
定时 check: 收集卡 → 过滤 → 调制 → 抽卡 → 目标选择 → 违抗roll → job
                    ↓
事件 → 判定(COC骰子) → 结果 → 日志 / 熟练度 / 记忆
```

**槽位（Slot，凹小人的地基）**：

| 属性 | 说明 |
|---|---|
| 数量/布局 | DNA 决定；信仰/成长可解锁潜能槽 |
| 类型 | 基础槽（生理保底）/ 系列槽（限定系列）/ 通用槽 |
| 容量 | 单卡槽 / 多卡槽（卡组，内部按权重抽） |
| 优先级 | 紧急槽 > 常规槽 > 自由槽（P1 启用，多层决策） |
| 状态 | 激活 / 休眠（事件或条件控制） |

**卡（Card，统一模型）**：

| 属性 | 说明 | 例 |
|---|---|---|
| 来源 | 天赋（DNA，不可移除）/ 技能（学习）/ 习惯（养成）/ 神谕（信仰插入） | — |
| 功能 | 行为卡（抽中→做 job）/ 修正卡（改概率）/ 目标卡（行为+目标选择） | — |
| 系列 | 战斗 / 工作 / 社交 / 宗教 / 娱乐 / 生理 | — |
| 情境 | 时段（白天/黑夜/全天）+ 事件 / 位置 / 心情条件 | 战后祈祷（事件=战斗后） |
| **卡属性** | **黑夜加成 / 白天加成 / 工作兴趣加成 / 战斗兴趣 / 社交兴趣 / 耐寒 / 耐热……** | 夜猫子=黑夜加成 2.0；热爱工作=工作兴趣 1.5 |
| 权重 | 基础触发概率 | — |
| 熟练度 | 0-100：触发↑ 遗忘↓，影响权重与效果 | — |
| 解锁 | 信任度 / 技能 / 事件 | 神谕策略卡需信仰解锁 |

**卡属性（stat modifiers）双用途**：

- **概率调制**：check 时参与加权（黑夜加成 × 黑夜时段；工作兴趣加成 × 工作系列行为）
- **判定修正**：COC 检定加成（耐寒→严寒环境检定 +；战斗兴趣→战斗检定 +）

**基础卡（人人固有，可被替换）**：黑夜睡觉、白天干活、饥饿进食、受伤治疗——生理保底不靠卡（紧急度由状态调制保证）。插"夜猫子"顶掉"黑夜睡觉" → 昼夜节律被改写。

**卡相互作用**（P0.5+）：

- **协同**：夜猫子 + 入夜警戒 → 夜间战斗力强化（卡组 = 神谕的构筑题）
- **冲突**：贪婪卡 vs 禁偷教义 → 教义赢，但产生"诱惑"事件（恶意槽 +）
- **占据**：大卡锁定系列（战争狂热 → 该系列其他卡让位）

**卡演化**（P0.5+）：

- 熟练度：触发↑ / 长期不用↓ → 权重和效果随之变化（卡 = 习惯的建模）
- 进化：熟练满 → 蜕变（"射箭熟练"→"箭术大师"）
- 腐化：恶意槽污染卡（"祈祷"→"伪善祈祷"——行为不变，意图变了）

**定时 check 机制**：

- 决策定时器每 tick 递减，**归零 → check 一次**，抽下一个 job；job 完成 → 立即 check（接续）
- 定时器间隔 = def 数据（如每 0.5 游戏日），可受状态影响（无事可做时更频繁 check）
- 与欲望 checkpoint 同源：都是"每隔一段时间运行一次"的检查器

**check 流程（抽 3 选 1）**：

```
1. 过滤：教义排除 / 情境不满足 / 未解锁
2. 调制权重：P = 卡属性(时段/兴趣加成) × 环境调制(气温/天气) × 状态调制(饥饿/疲劳/健康/SAN/心情) × 马尔可夫(上一事件) × 卡权重 × 熟练度
3. 按权重抽 3 张（不放回，种子化）
4. 收益表（每日重算一次）→ 挑收益最高的卡
5. 目标卡 → 目标选择（目标池按概率：对谁传教、打谁）
6. 违抗 roll（可选）：欲望卡被抽到但没被选 → roll 改选欲望卡
7. 生成 job → 事件 → 骰子判定 → 结果 → 日志 / 熟练度 / 权重调整
```

- **环境调制**：气温（酷暑 → 户外干活低、饮水高；寒冬 → 囤燃料）、天气（下雨 → 户外干活低、室内活动高）
- **状态调制**：饥饿 → 进食；疲劳 → 休息；健康低 → 治疗；SAN 低 → 疯癫行为进候选池；心情差 → 娱乐/发泄
- **马尔可夫**：上一事件偏置（刚打完架 → 战斗训练/休息概率上升）

**P0 范围**：槽位类型+容量、卡属性（时段/兴趣加成）、情境（时段）、行为卡+修正卡。**P0.5**：熟练度/进化/腐化、协同/冲突/占据、目标卡。**P1**：优先级分层（多层决策）。

```ts
// sim/core/rng.ts —— 种子 RNG（确定性）
export class SimRng {
  private s: number;
  constructor(seed: number) { this.s = seed >>> 0; }
  next(): number {            // xorshift32
    let x = this.s;
    x ^= x << 13; x >>>= 0;
    x ^= x >> 17;
    x ^= x << 5; x >>>= 0;
    this.s = x;
    return x;
  }
  d100(): number { return this.next() % 100 + 1; }
}

// sim/ai/cards.ts —— 插槽系统（槽位 + 策略卡，数据驱动 + 注册表）
type Sin = 'gluttony'|'sloth'|'greed'|'envy'|'pride'|'wrath'|'lust';

// 系列 = 字符串 id + defs 注册（不是 union type——mod 加系列不改核心代码）
interface SeriesDef { id: string; label: string; }

// 卡属性 = 任意字符串键 → 数值字典（mod 加新属性不改 interface）
interface Card {
  id: string;
  source: 'talent' | 'skill' | 'habit' | 'oracle';  // 来源
  func: 'behavior' | 'modifier' | 'target';         // 行为/修正/目标卡
  series: string;                                    // 系列 id
  job?: string;                                      // 行为卡：对应 job
  situation: { period: 'day'|'night'|'all'; event?: string; };  // 情境
  stats: Record<string, number>;                     // 卡属性字典
  weight: number;                                    // 基础触发权重
  mastery: number;                                   // 熟练度 0-100（P0.5）
  unlock?: (p: PawnState) => boolean;                // 解锁条件
}

interface Slot {
  id: string;
  kind: 'basic' | 'series' | 'generic';   // 基础/系列限定/通用
  series?: string;                        // 系列槽限定
  capacity: number;                       // 卡容量（卡组）
  priority: 'urgent' | 'normal' | 'free'; // 紧急/常规/自由（P1 启用）
  cards: Card[];                          // 卡组（内部按权重抽）
  active: boolean;
}

// —— 注册表（mod 的全部入口，核心 checkJobs 永不改动）——
interface ModifierCtx {
  pawn: PawnState; env: EnvState; prevEvent: string;
  seriesOf: (c: Card) => string;
}
type ModifierFn = (ctx: ModifierCtx, card: Card) => number;

const seriesRegistry = new Map<string, SeriesDef>();
const cardRegistry = new Map<string, Card>();
const modifierRegistry = new Map<string, ModifierFn>();
const hooks: Record<string, Array<(prob: Record<string, number>, ctx: SimContext) => void>> = {};

export function registerSeries(def: SeriesDef) { seriesRegistry.set(def.id, def); }
export function registerCard(card: Card) { cardRegistry.set(card.id, card); }
export function registerModifier(name: string, fn: ModifierFn) { modifierRegistry.set(name, fn); }
export function registerHook(stage: string, fn: (prob, ctx) => void) { (hooks[stage] ??= []).push(fn); }

// 内置调制器（mod 可新增/覆盖，属性名 = 注册键，与卡的 stats 键一一对应）
registerModifier('night-bonus', ({ env }) => env.night ? 2 : 0.3);
registerModifier('day-bonus',   ({ env }) => env.night ? 0.3 : 2);
registerModifier('cold-resist', ({ env }, c) => env.temperature < -10 ? 1 + (c.stats['cold-resist'] ?? 0) : 1);
// 兴趣加成：只对对应系列生效（work-interest 只作用于 work 系列卡）
registerModifier('work-interest',   ({ seriesOf }, c) => seriesOf(c) === 'work'   ? (c.stats['work-interest'] ?? 1) : 1);
registerModifier('combat-interest', ({ seriesOf }, c) => seriesOf(c) === 'combat' ? (c.stats['combat-interest'] ?? 1) : 1);
// 例：mod 加"魅力加成" = registerModifier('charm-bonus', fn) + 卡 stats 写 'charm-bonus'，核心零改动

// 卡属性 → 概率调制：遍历卡 stats 字典，按属性名查调制器相乘
function cardFactor(ctx: ModifierCtx, card: Card): number {
  let f = 1;
  for (const [name, v] of Object.entries(card.stats))
    if (modifierRegistry.has(name)) f *= modifierRegistry.get(name)(ctx, card) * v;
  return f;
}

interface PawnState {
  hunger: number;      // 0-100 越饿越高
  tired: number;       // 0-100 越累越高
  health: number;      // 0-100 越低越伤
  san: number;         // 0-100 理智
  mood: number;        // 0-100 心情
  desire: Record<Sin, number>;       // 七宗罪满足度 0-100
  personality: Record<Sin, number>;  // 罪孽倾向 0-100
  obedience: number;                 // 顺从度
}

interface SimContext {
  prevEvent: string;                 // 上一个事件（马尔可夫状态）
  env: EnvState;                     // 环境：昼夜/气温/天气
  slots: Slot[];                     // 槽位（含卡组）
  doctrine: Set<string>;             // 教义禁止集合
}

// 状态调制：生理/心理紧急度提升对应行为概率（内置函数，也可注册化为调制器）
function stateFactor(p: PawnState, c: Card): number {
  switch (c.series) {
    case 'physio':  return 1 + Math.max(p.hunger, p.tired, 100 - p.health) / 40;
    case 'leisure': return 1 + (100 - p.mood) / 100;   // 心情差 → 娱乐
    default: return 1;
  }
}

// 环境调制：气温/天气（内置函数）
function envFactor(ctx: SimContext, c: Card): number {
  const e = ctx.env;
  if (c.series === 'work')
    return (e.raining ? 0.4 : 1) * (e.temperature > 35 || e.temperature < -10 ? 0.5 : 1);
  if (c.series === 'leisure') return e.raining ? 1.6 : 1;
  return 1;
}

// 马尔可夫偏置表：上一事件 → job 偏置（def 数据，mod 可改，未列出的默认 10）
const MARKOV_BIAS: Record<string, Record<string, number>> = {
  fight: { 'train-combat': 40, rest: 20, eat: 15 },
  haul:  { 'mine': 40, build: 30, eat: 10 },
  pray:  { preach: 40, 'train-combat': 15, work: 20 },
  // ...
};

function checkJobs(p: PawnState, ctx: SimContext): Record<string, number> {
  const prob: Record<string, number> = {};
  for (const slot of ctx.slots) {
    if (!slot.active) continue;
    for (const c of slot.cards) {
      if (!situationOk(c, ctx) || ctx.doctrine.has(c.job)) continue;   // 情境 + 教义排除
      prob[c.job] =
        cardFactor(ctx, c)                               // 卡属性（注册表调制器）
        * envFactor(ctx, c)                              // 环境调制（气温/天气）
        * stateFactor(p, c)                              // 状态调制（饥饿/疲劳/健康/心情）
        * (MARKOV_BIAS[ctx.prevEvent]?.[c.job] ?? 10)    // 马尔可夫偏置
        * c.weight                                       // 卡权重
        * (0.5 + c.mastery / 100);                       // 熟练度（P0.5）
    }
  }
  hooks['beforeRoll']?.forEach(h => h(prob, ctx));       // 阶段钩子（mod 插入）
  return normalize(prob);
}

// 抽取：种子 RNG，确定性
function weightedRoll(prob: Record<string, number>, rng: SimRng): string {
  const total = Object.values(prob).reduce((a, b) => a + b, 0);
  if (total <= 0) return 'idle';
  let r = rng.next() % total;
  for (const [job, w] of Object.entries(prob)) {
    r -= w;
    if (r < 0) return job;
  }
  return 'idle';
}

// 收益：每日重算一次（1day1次），局势评估——饥饿/环境/目标/事件修正（def 数据）
function computeUtility(p: PawnState, ctx: SimContext, c: Card): number {
  let u = 0;
  if (c.series === 'physio')   u += Math.max(p.hunger, p.tired, 100 - p.health) / 2;
  if (c.series === 'work')     u += ctx.taskUrgency(c.job);       // 派系任务紧迫度
  if (c.job === 'pray')        u += ctx.nearChurch() ? 20 : 0;    // 教堂影响圈内
  u += ctx.eventBoosts[c.job] ?? 0;                               // 事件调整收益
  return u;
}

// 每日重算收益表
function updateUtilities(p: PawnState, ctx: SimContext) {
  for (const c of ctx.cardPool) c.utility = computeUtility(p, ctx, c);
}

// 抽 3 选 1：按权重抽 3 张（不放回），挑收益最高
function pickJob3(prob: Record<string, number>, rng: SimRng): string {
  const drawn: string[] = [];
  const pool = { ...prob };
  for (let i = 0; i < 3 && Object.keys(pool).length > 0; i++) {
    const job = weightedRoll(pool, rng);
    drawn.push(job);
    delete pool[job];                          // 不放回
  }
  return drawn.reduce((best, j) =>
    utilityOf(j) > utilityOf(best) ? j : best, drawn[0]);
}

// 决策定时器：归零或 job 完成 → check
export function tickPawnDecision(p: PawnState, ctx: SimContext, rng: SimRng): string | null {
  ctx.timer -= 1;
  if (ctx.timer > 0 && !ctx.jobJustFinished) return null;
  ctx.timer = ctx.checkInterval(p);            // 重置定时器（def 数据）
  if (ctx.dayRolled) updateUtilities(p, ctx);  // 每日重算收益（1day1次）
  return pickJob3(checkJobs(p, ctx), rng);     // 抽 3 选 1 → 新 job
}
```

**确定性保证**：sim 主 RNG 流 = `new SimRng(世界种子 ^ tick)`,所有 roll/骰子共用同一流按序取——回放只需重放外部输入（命令/事件）即可复现。

### LLM 上下文打包：世界摘要 + 三层记忆

LLM 的上下文不能塞整个世界，参考 RimWorld RimMind 模组（已被社区验证）分层打包：

| 层 | 内容 | 存续 |
|---|---|---|
| 活跃记忆 | 近期事件（按时间排序，容量上限） | 短期 |
| 存档记忆 | 按重要度排序，满时淘汰低重要度条目 | 中期 |
| 长期印象（暗记忆） | AI 每日凝练 ≤50 字摘要，永久保留 | 长期 |

- 每次 LLM 请求 = **世界摘要**（派系/城镇/经济/威胁的压缩状态）+ 相关事件史 + 目标个体记忆 + 神谕影响
- 只在事件节点打包，控制 token（参考：RimWorld 实测每事件 7k-13k token，5 年约 2M token）
- 记忆由 sim 事件自动采集（工作/受伤/死亡/关系/派系事件），非手动编写

### 叙事压力（narrative pressure）

LLM 天然爱重复生成同类事件，需要确定性计数器约束多样性：

- 记录"距上次袭击/贸易/疾病/来访 X 天"，生成压力值进入 prompt
- 例：45 天无袭击 → 战斗类压力高 → 即使殖民地平和也倾向触发冲突事件
- 事件多样性靠计数器逼出来，不靠提示词

### 小人社交对话与流言系统（狗屁倒灶）

小人之间的闲聊八卦、勾心斗角是乐趣核心之一，也让社会显得真实可笑。参考 RimMind-Dialogue（拦截社交事件 → LLM 生成上下文对话 → 效果注入心情/关系，已有先例）。

**频率分层（成本关键）**：

| 层级 | 内容 | 生成方式 |
|---|---|---|
| 微互动 | 碰面打招呼、抱怨、表情 | 确定性模板（高频、零成本） |
| 闲聊 | 引用近期事件/记忆的对话 | LLM 批量生成（服务端异步，无人等待） |
| 深聊/冲突 | 关系变化、重大事件、背叛 | LLM 按需调用（低频、重要节点） |

- 每小人每日 LLM 对话限额，超限回落模板
- 对话必须引用记忆（三层记忆是素材库），否则空洞

**对话 = 流言系统（产物是"话题"，不是文本）**：

- 一次对话产出话题单元：谁、对谁、说了什么、涉及谁
- 话题沿社交网络传播（八卦），传播改变他人对该小人的看法（名声/信誉）
- 流言 → 关系 delta + 心情 thought + 记忆条目，闭环进系统（Smallville 已验证：LLM 社会能自发产生信息扩散）

**神谕窗口**：

- 对话/流言日志是玩家可读的观察窗口（"文明新闻流"的微观层）
- 神谕可通过教堂布道影响话题传播方向（引导舆论，间接干预）

**效果挂钩系统（不是装饰）**：对话必须落成关系变化/心情 thought/记忆条目，否则小人只是说话机器。

## 7. 插件/mod 系统（与联机的冲突点）

### 分层原则：服务端 mod（逻辑）+ 客户端 mod（表现）

| 层 | 谁能写 | 内容 | 在哪里执行 |
|---|---|---|---|
| 服务端 mod | 房主/服主 | 物品、新 AI、新事件、新 job、新建筑、新神谕能力 | **只有服务端执行** |
| 客户端 mod | 任意客户端 | 渲染表现、UI、立绘、音效 | 客户端本地（不影响逻辑） |

保证：**逻辑统一在服务端，客户端 mod 只是皮肤**，联机一致性不被破坏。

### 数据驱动注册表（defs）

```ts
registerDef({ kind: 'item', id: 'steel', stackable: true });
registerDef({ kind: 'building', id: 'solar-panel', size: 3, power: 30 });
registerBehavior({ kind: 'ai', id: 'my-pawn-ai', decide: (ctx) => Intent });
registerEvent({ kind: 'event', id: 'wanderer-arrives', weight: 2 });
registerOracle({ kind: 'oracle', id: 'bless', cost: 10, effect: (ctx) => ... });
// 插槽系统（见 §6）：系列/卡/调制器/钩子全部注册表化
registerSeries({ id: 'research', label: '研究' });
registerCard({ id: 'study-late', series: 'research', stats: { 'night-bonus': 2 } });
registerModifier('charm-bonus', (ctx, card) => ...);   // 新卡属性 = 新调制器，核心零改动
registerHook('beforeRoll', (prob, ctx) => ...);          // check 流程阶段钩子
```

**扩展性原则（核心 sim 代码永不改动）**：

- 加新卡属性 = `registerModifier` + 卡 stats 加键，不改 interface/switch
- 加新系列 = `registerSeries` + 卡 def，不改 union type
- 加新卡 = `registerCard` 纯数据（除非要新行为逻辑）
- 调平衡 = 改 def 数值，不重编译
- 加 check 阶段 = `registerHook`
- 验证标准：**任何 mod 能力都应能通过注册表实现，不需要改 sim 源码**；做不到的注册表接口，是 sim 的缺陷

- 服务端加载 mod → 注册进注册表 → 流式下发 defs 给客户端（只读副本）
- 版本校验：客户端 defs hash 必须匹配，否则拒绝加入

### 物品
- 物品 = 数据（id、可堆叠、质量、标签）+ 可选行为钩子
- 存储在地块/库存中，由 job 系统搬运
- mod 新增物品 = 一个 def，零代码（除非要新行为）

### 新 AI
- 新 AI = 注册一个新的 `decide` 函数（纯逻辑，双端共享）
- 服务端 mod 可替换/叠加小人决策逻辑，或**新增派系 AI**
- 客户端不能执行 mod AI（一致性），只能收到结果

## 8. 网络协议（WSS，Node server）

- 传输 WSS，JSON 帧起步，性能不够换二进制（msgpack）
- Node 侧用 `ws` 起步，压不动换 `uWebSockets.js`
- C→S：`join` `command(move/build/harvest)` `oracle(施加神谕)` `speed/pause` `ping`
- S→C：`world snapshot` `tick delta` `entity events` `chunk data` `world clock` `defs(只读)`
- sim 双端同源，协议类型定义在 `src/shared/protocol.ts`，无需双实现

**生产（§3 咬合）**：伐木/采矿 = 进度 + 骰子产出（`GatherSystem`）；矿洞 = 持续产矿（饥荒式矿场，40s 一轮）；农田 = 自动产粮；工作台 = 木→工具（采集 ×1.3）。产出受 STR 力量加成、工具加成。

**卡系统（§6）**：抽 3 选 1（种子化不放回）+ 收益择优；权重调制 = 天赋卡（工作兴趣/懒惰）× 欲望驱动（匮乏欲望升权）× 环境调制（雨/极端气温）× 马尔可夫偏置（上一系列）。违抗 roll 仅工作卡被选且有未选本我卡时触发，30s 冷却防刷屏。

**COC 骰子（§3）**：八属性全量；事件骰 = `roll ≤ dc + INT 加成`；技能检定 `rollEventSkill` = `dc + 技能/10`；技能成长 = 用后掷 d100 > 当前 → +1d10。

**七宗罪（§3）**：P0 版满足度 + 先天倾向（DNA.sins）；吃→暴食、休息→懒惰、工作→贪婪、祈祷→傲慢；恶意槽 = 长期匮乏 → 偷窃/砸建筑/暴躁。

**环境（§6）**：气温随昼夜波动 + 雨-晴循环；调制卡权重（下雨户外工作 ×0.5、娱乐 ×1.6；酷暑/严寒户外工作 ×0.6、生理 ×1.3）。

**叙事压力（§6）**：和平越久袭击越猛（间隔缩短 + 规模/血量放大），和平→压力→冲突闭环。

**社交（§6 微互动）**：相遇 → 打招呼/抱怨/表情，心情 + 好感度双向变化，话题抽自结构化历史（狗屁倒灶）。

**历史（§3）**：所有 GameEvent → 结构化条目（时间/类型/实体/地点/原因/事实），可查询可导出；LLM 只润色原则就位。

**mod（§7）**：ModRegistry 运行时注册 tile/building/item/enemy/card/recipe/event/expansionPlan/intent/work/system/hook + overrideDef/overrideTuning，冲突检测；`SimOptions.mods` 构造期挂载。**客户端 mod 表现**：UI 全部走 defs（建造菜单/tile 渲染/建筑图标/sprite 声明/敌人散列色），`?mods=url` 运行时加载 ESM mod（demo: src/mods/demo-berry.ts，e2e: scripts/e2e/mod-ui.mjs）。

**存档**：IndexedDB（异步、大容量），30s 自动存档；含社会单位（派系/记忆/看法/库存/玩家所属/成员归属）持久化。

**指派职业/生产线（用户 Q10）**：HUD 选中小人 → 指派"伐木工/矿工/农民/工匠/自由"；指派后对应工作卡权重 6x、其他 0.1x，自动补卡进池——形成"基础支持（食/木/矿）→高级支持（工具）→奇观"的分工。

**奇观（用户 Q10）**：纪念碑（木60+矿25，buildTime 40s），建成后全营地心情光环（敬畏）。

**社会单位/篝火派系（用户 Q9 + 即时指令）**：有篝火 = 独立派系。篝火维护部落记忆 + 对其他单位的看法（容量：篝火 2-3、教堂 5-10）。**教堂 = 篝火升级**。篝火间信任机制：成员协作→看法↑；双向友好→贸易（供需汇率 + 逆差记账）；双向敌对→派掠夺者攻打；中性→传话（只有传话，不直接控制）。**逆差→怨恨→战争**联动；征服（摧毁核心→吞并）；**派系 = 单位间的看法关系**（友好→贸易/伙伴、敌对→战争，无抽象联盟层）；野生篝火事件刷新新势力。

**团灭附身（用户 Q3）**：玩家单位成员清零或被征服 → 神谕自动附身最近存活单位。

**渲染**：PixiJS v8 + SVG（data-uri → GraphicsContext，矢量不糊）；**2D 俯视 ↔ 2.5D 同轴可切换**（2.5D 按世界 y 排序前后遮挡）。
